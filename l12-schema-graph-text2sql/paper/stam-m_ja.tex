\begin{abstract}
無機材料データベースはSQLの知識を前提としており、材料研究者にとってデータ活用の大きな障壁となっている。
本研究では、この障壁を取り除き、材料工学におけるSQLデータ活用に自然言語からの活路を開くため、無機材料向けリレーショナルデータベース（RDB）の自然言語アクセスを実現するText-to-SQLパイプラインの設計原理を提示し、その有効性を実証する。
提案手法は、(i) few-shot例検索、(ii) 大規模言語モデルによるSQL生成、(iii) 外部キーグラフに基づくSteiner木JOIN制約、(iv) 材料ドメイン辞書、(v) 抽象構文木解析ベースのSQL安全性検証（SQLGuard）、(vi) LLMリランカーの6要素から構成される。

B2/L1$_2$/NaCl 等を含む31テーブル・約2万行のRDBを用いた多軸評価では、実行再現率84.7\%、適合率77.3\%、F1値74.8\%の抽出精度を達成した。
SQLGuardによる非SELECT文の排除と構文妥当率100\%は安全性を担保する。
4種類のゼロ適応転用試験（プロトタイプ拡張（A）90.0\%、OQMD風命名変更（B）90.5\%、ランダム化名前転用（C）90.0\%、実在するMaterials Project風スキーマ（D）100.0\%）に成功し、保守性・汎化性を示した。
さらに100件の評価クエリを用いた7条件のablation study（5独立ラン）で、few-shot例と材料ドメイン辞書がそれぞれ$-$7.4\,pp（$p<0.001$）、$-$7.3\,pp（$p<0.001$）と統計的に有意な精度向上を示すことを確認した。
15パターンのCTE多段計算（純物質基準からの生成エンタルピー計算を含む）により、単なる情報検索を超えた導出計算の可能性を実証し、独立設計100件の外部検証（76.9\%）も合わせて、材料研究者がSQLを記述しなくてもクロステーブル探索・工学的問いかけができる研究インフラの実現を示した。
\end{abstract}

\section{はじめに}
\label{sec:introduction}

\paragraph*{無機材料研究におけるデータ探索の障壁}

無機材料研究は、高スループットの第一原理計算の進展により、データ駆動型の材料発見へと移行している。OQMD~\cite{saal2013oqmd,kirklin2015oqmd}、Materials Project~\cite{jain2013mp}、AFLOW~\cite{curtarolo2012aflow}、NOMAD~\cite{draxl2019nomad}、およびAtomWork-Adv~\cite{nims2018atomworkadv}のようなデータベースは、組成、結晶構造、電子状態、熱力学的安定性をカバーする数万から数十万の計算記録を保存している。

これらのデータは通常、SQLを介した柔軟なクロステーブルクエリのために設計された正規化されたリレーショナルデータベース（RDB）に保存される。DFTデータベースには、個別エントリの取得や定型的な計算を行うAPIも備わっていることが多いが、APIは複数テーブルを跨ぐ複雑な条件検索や大規模な統計処理には向かない。一方、SQLやSQLを自然言語から生成するText-to-SQLは、データベースの構造（リレーション）を直接活用できるため、高度な抽出や集計といった研究における探索的な問いに対して、より柔軟かつ強力に応答する。しかし、RDBを利用するには、テーブル構造、外部キー（FK）関係、およびSQL構文を理解する必要があり、関連するデータが存在することを知っていてもアクセスできない材料研究者にとっては大きな障壁となる。その結果、研究者が自然言語でクエリを実行できないため、貴重なデータが十分に活用されていない。

\paragraph*{自然言語データベースインターフェースの重要性}

この障壁の本質は、SQL記述の技術的要件がドメイン知識とデータの間に介在していることである。自然言語インターフェースは、SQLの代替となる便利なツールではなく、データアクセスの障壁を根本的に減少させ、研究を加速することができる研究インフラの一部である。

無機材料のRDBでは、正規化により数十のテーブルが生成され、複数のテーブルを含むJOINを構築することは、経験豊富なSQLユーザーにとっても困難である。自然言語から適切なSQLが自動的に生成できれば、材料研究者はスキーマ構造を意識することなくクロステーブルデータ探索を行うことができる。

スキーマの変更やテーブルの追加を完全に自動で追跡するシステムを構築することは現在困難だが、FKメタデータに依存する設計を採用することで、スキーマの進化への適応が比較的容易になる。

\paragraph*{Text-to-SQL技術と材料科学における現状}

Text-to-SQL技術は、Spider~\cite{yu2018spider}やBIRD~\cite{li2024bird}のようなベンチマークを中心に発展してきた。最近の大規模言語モデル（LLM）の進展に伴い、DIN-SQL~\cite{pourreza2024dinsql}はスキーマリンク、分類、生成を分離したパイプラインアプローチを提案した。DAIL-SQL~\cite{gao2023dail}は、少数ショットの例選択戦略に焦点を当てた。RAT-SQL~\cite{wang2020ratsql}は関係認識エンコーディングを導入し、RESDSQL~\cite{li2023resdsql}はスキーマリンクのデカップリングを導入した。SchemaGraphSQL~\cite{safdarian2026schemagraphsql}は、FKグラフ上のパス探索を使用している点で、我々の研究に最も近い。

しかし、これらの方法は一般的なベンチマークで評価されており、特に無機材料データベースのドメイン特化型RDBには適用されていない。このため、材料工学のデータベースにおいてこれらの手法がどの程度の効果をもたらすかはよくわからなかった。MatSciBERT~\cite{gupta2022matscibert}やMatBERT~\cite{walker2021matbert}は材料科学テキスト用の言語モデルだが、Text-to-SQLタスクに直接適用されていない。MKNA~\cite{zhuang2026mkna}やOptiMat~\cite{hu2026optimat}はAPIベースのアクセスを提供するが、正規化されたRDBに対してJOIN制御を伴うSQL生成を行わない。SuperCon~\cite{ishii2023supercon}やPoLyInfo~\cite{ishii2024polyinfo}は強力な意味論的推論を伴うRDF/SPARQLベースのオントロジーアプローチを採用しているが、既存のRDBインフラに適用するためにはデータ変換が必要だ。

\paragraph*{目的と貢献}

本研究の目的は、無機材料RDBへの自然言語アクセスを可能にする設計原則を提示し、その有効性を検証することである。我々は、材料研究者がSQLやスキーマ構造を意識することなくデータを探索できる方法論を示し、OQMDから抽出したデータを元に作成したRDBを例として、自然言語クエリがどの程度処理できるかを検討する。

本研究で扱う3つのドメイン特有の課題は次のとおりだ：
\begin{enumerate}
  \item ドメイン用語の曖昧さ：
    結晶構造名やL1$_2$、$\gamma'$相、B2のような特性用語は、一般的なLLMのトレーニングデータに十分に表現されておらず、SQL条件への正確な変換が困難である。
  \item 複数テーブルJOINの複雑さ：
    正規化された材料RDBは数十のテーブル間でJOINを必要とし、LLMによるJOINの幻覚のリスクが高まる。
  \item 評価データの欠如：
    無機材料RDBにおけるText-to-SQLのための標準評価ベンチマークは存在しない。
\end{enumerate}

我々の貢献は4つある：
\begin{enumerate}[label=(\roman*)]
  \item 材料RDB Text-to-SQLのための設計原則：
    我々は、FKグラフ上のSteiner-tree JOIN制約、材料ドメイン辞書、およびハイブリッドリランカーを統合したパイプラインを提案する。
    これは、材料特有の用語翻訳が欠如している一般的なText-to-SQL手法（DIN-SQL、DAIL-SQL、SchemaGraphSQLなど）と、RDB/SQLを対象としない材料NLアクセスシステム（MKNA、OptiMatなど）とのギャップを埋める。
  \item 多軸定量評価：
    B2/L1$_2$/NaCl 等を含む31テーブル・約2万行のRDBに対する7条件$\times$100クエリ$\times$5回の統計的アブレーション（ウィルコクソン符号付き順位検定）を超えて、少数ショットの$k$感度、辞書サイズ感度、LLMモデル比較、および多軸メトリクス（EM / SELECT列精度 / JOIN一致率）を提供する。
  \item ドメイン知識の定量的効果：
    材料辞書（$-$7.3\,pp, $p<0.001$）と少数ショット例（$-$7.4\,pp, $p<0.001$）が統計的に有意な寄与を持つことを示し、ドメイン特化型モジュールの必要性を検証する。
  \item スキーマ一般化のデモンストレーション：
    四つのスキーマバリアントにわたるゼロ適応転送テスト---A~プロトタイプ拡張（90.0\%）、B~OQMD風の名前変更（90.5\%）、C~ランダム化された難読化（90.0\%）、およびD~Materials Project風のスキーマ（100.0\%）---は、FKイントロスペクションに基づく設計原則が特定のスキーマに依存しないことを示している（セクション~\ref{sec:transfer_eval}）。
\end{enumerate}

\subsection{少数ショット例の検索}
\label{sec:fewshot}

入力クエリに類似した少数ショット例は、2段階で選択される。
まず、TF-IDF~\cite{salton1988tfidf}が候補を$2k$アイテムに絞り込み、
次にクロスエンコーダ（ms-marco-MiniLM-L-6-v2）が上位$k$を選択する。
クロスエンコーダはローカルで実行され、処理時間は50\,ms未満である。

選ばれた少数ショット例は、テーブル名、JOIN順序、列名の使用などのSQL生成パターンを示す。これにより LLM はインコンテキスト学習~\cite{brown2020fewshot}を通じて、スキーマ情報だけでは決まらない具体例に基づいた生成を安定させる。

\subsection{スキーマリンク}

GPT-5.5は入力クエリに関連するテーブルをスコアリングし、ソートする。テーブルは除外されず、SQL生成のためのコンテキスト優先順序のみが変更される。

\subsection{SQL生成と$n$-best候補}

ここでの ``$n$-best'' は、LLMが1回の生成呼び出しで上位 $n$ 個の SQL 候補を並列に出力し、後段のリランカーでその中から最適な 1 本を選択する仕組みを指す。多数の候補を生成すると回答レイテンシが増大するため、本実装では $n$-best = 3 をデフォルトとした。

GPT-5.5は$n$-best = 3のSQL候補を生成する。候補数を増やすと解釈空間は広がるが、レイテンシも増大する。後段のリランカーが上位 1 本を選択し、残りは廃棄する。  
\subsection{シュタイナー木JOIN制約}
\label{sec:schema_graph}

31のテーブル間のFK関係は、NetworkX~\cite{networkx2008}を使用して無向グラフ $G=(V,E)$（$V$はテーブルの集合、$E$は外部キー（FK）関係の集合）として表現される。FK関係は、PostgreSQLメタデータのイントロスペクションを介してランタイムで自動的に取得される。クエリに必要なテーブルのセットに対して、最小JOIN部分木はシュタイナー木近似を介して決定される（アルゴリズム~\ref{alg:steiner}に示す通り）。

\begin{algorithm}[htbp]
  \caption{最小被覆JOIN部分グラフ（シュタイナー木近似）。}
  \label{alg:steiner}
  \begin{algorithmic}[1]
    \Require FK関係グラフ $G = (V, E)$, 必要なテーブルセット $R$
    \Ensure JOINパスリスト $P$
    \State $P \gets \emptyset$; ユニオンファインド $U$ を初期化
    \ForAll{$(s, t) \in \binom{R}{2}$}
      \If{$\text{Find}(s) = \text{Find}(t)$}
        \State continue
      \EndIf
      \State $p \gets \text{ShortestPath}(G, s, t)$ \Comment{FKグラフ上のBFS}
      \If{$p \neq \emptyset$}
        \State $P \gets P \cup \{p\}$
        \ForAll{隣接ノードペア $(u, v) \in p$}
          \State $\text{Union}(u, v)$
        \EndFor
      \EndIf
    \EndFor
    \State \Return $P$
  \end{algorithmic}
\end{algorithm}

ノード数 $|V| = n$ および必要なテーブル数 $|R| = k$ に対して、アルゴリズムは $O(k^2)$ のBFSトラバーサルを実行する。31テーブル規模（$n = 31$, $k \leq 5$）では、これがミリ秒単位で完了する。

シュタイナー木は、必要なテーブル集合を連結する最小被覆 JOIN パスを導くことで、余分なテーブルや自己結合の混入を防ぐ。FK 関係はランタイムで PostgreSQL メタデータから取得されるため、スキーマの追加や変更に対して自己反映的に対応する。

\subsubsection{PostgreSQLメタデータからのグラフ構築}

FK関係は、PostgreSQLの\texttt{information\_schema}からランタイムで動的に抽出される。

\begin{lstlisting}[language=SQL,caption={FK関係の抽出},label=lst:fk_query,numbers=none]
SELECT tc.table_name, kcu.column_name,
       ccu.table_name, ccu.column_name
  FROM information_schema.table_constraints tc
  JOIN information_schema.key_column_usage kcu
    ON tc.constraint_name = kcu.constraint_name
  JOIN information_schema.constraint_column_usage ccu
    ON ccu.constraint_name = tc.constraint_name
 WHERE tc.constraint_type = 'FOREIGN KEY';
\end{lstlisting}

結果は、NetworkX~\cite{networkx2008}において無向グラフ $G = (V, E)$ として保存される。各エッジは、JOIN句生成時に使用される属性としてFKの方向を保持する。FKメタデータはランタイムで読み取られるため、システムはスキーマの変更を追跡できる。

\subsubsection{複数要素ANDクエリ：EXISTSサブクエリ}
\label{sec:multi_element}

構成テーブルの正規化から生じる材料特有の課題は、「NiとAlの両方を含む化合物」のようなクエリである。単純なアプローチ\texttt{WHERE c.element = 'Ni' AND c.element = 'Al'}は、どの行も両方の条件を満たさないため、常に0行を返す。スキーマグラフエンジンは、複数の要素が指定されているときにそれを検出し、自動的にEXISTSサブクエリを生成する：

\begin{lstlisting}[language=SQL,caption={複数要素AND},label=lst:exists,numbers=none]
SELECT DISTINCT m.entry_id, m.formula
FROM material_entry m
WHERE EXISTS (SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Ni')
AND EXISTS (SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Al')
LIMIT 10000;
\end{lstlisting}

AND/ORの意図は、結合と助詞から条件抽出器によって分類される。OR指標には、\texttt{IN}句が使用される。

\subsubsection{JOINパスからのSQL生成}

$P$は、アルゴリズム~\ref{alg:steiner}によって求められた最小被覆 JOIN パス（Steiner 木）に含まれるエッジ集合である。$P$内の各パスはSQL JOIN句に変換される。テーブルエイリアスは、すべての31テーブルに対して固定辞書から割り当てられる（\texttt{material\_entry}$\to$\texttt{m}, \texttt{composition}$\to$\texttt{c}など）。同じテーブルが複数回出現する場合、数値サフィックスがユニークなエイリアスを生成する（\texttt{c2}, \texttt{c3}）。

\subsection{条件抽出器}
\label{sec:entity_extractor}

条件抽出器は、自然言語クエリを構造化された条件辞書に変換する。これは、YAMLベースのバイリンガル（日本語-英語）用語辞書（\texttt{material\_terms.yaml}）を使用する。

\subsubsection{辞書構造}

条件抽出器は、対象とするRDBのテーブル・カラム構造を反映したバイリンガル（日本語-英語）用語辞書（\texttt{material\_terms.yaml}）を用いる。すなわち、\texttt{material\_entry}、\texttt{structure}、\texttt{composition}、\texttt{phase\_stability} などの実際のテーブルとそのカラムを踏まえて、自然言語表現とデータベーススキーマを対応付ける。

辞書は4つのカテゴリをカバーしている：
(1)~プロトタイプエイリアス（例：\texttt{L12} $\leftrightarrow$ [L1$_2$, Cu$_3$Au型, $\gamma'$]）、
(2)~元素マッピング（\texttt{Fe} $\leftrightarrow$ [鉄]）、
(3)~安定性用語（「安定」$\to$ \texttt{energy\_above\_hull} $\leq 0.001$~eV/atom; 「準安定」$\to$ $0.001 < E_\text{hull} \leq 0.05$）、
(4)~特性用語（「格子定数」$\to$ \texttt{structure.lattice\_a}など）。

Unicode下付き文字（U+2080--U+2089）は、マッチングの前にASCII数字に正規化される。元素記号の認識は、単語境界の正規表現を使用して「Fe」を「FeCoNi」の部分文字列から区別する。

\subsubsection{化学式パーサと曖昧さ処理}

化学式トークンは3つのタイプに分類される：
(1)~exact\_formula（\texttt{Ni3Al} $\to$ \texttt{formula = 'Ni3Al'}）、
(2)~formula\_or\_reduced\_formula（「NiAlのB2エントリ」$\to$ \texttt{reduced\_formula = 'AlNi'}）、
(3)~contains\_elements（「NiとAlを含む」$\to$ EXISTSサブクエリ）。
分類は文脈依存である：「含む」といった表現との共起は、\texttt{contains\_elements}処理を引き起こす。

\subsubsection{カバレッジスコア}
\label{sec:coverage_score}

カバレッジスコアは、辞書、元素辞書、または数値パターンによって認識されたクエリ内の意味トークンの割合を定量化し、$[0, 1]$の値を生成する。 このメトリックは、サイレント制約ドロップ（認識されない語彙の静的廃棄）を防ぐ。 スコアが$\geq 0.8$の場合、ルールベースモードの実行がトリガーされる； $\geq 0.5$の場合はLLMモードにエスカレートする； $< 0.5$の場合はユーザーからの確認を要求する。

\subsubsection{意図分類器}
\label{sec:intent_classifier}

ルールベースの意図分類器はSQL生成の上流に配置され、クエリを5つのカテゴリに分類する。これは、20のVASP/DFTワークフローパターンの正規表現マッチカウントを9のDB特有パターンと比較し、範囲外の質問を事前にフィルタリングする。

\subsection{SQLGuard}
\label{sec:sqlguard}

SQLGuard は sqlglot~\cite{sqlglot2023} によって生成された SQL を抽象構文木（AST）にパースし、その AST ノード（\texttt{Statement}, \texttt{Select}, \texttt{Column}, \texttt{Table}, \texttt{Join} 等）をトラバースすることで、安全性と一貫性を静的に検証する。sqlglot による AST 解析により、テキストレベルでは判別しにくいマルチステートメントの混入、テーブル・カラムの参照解決、サブクエリのネスト深さ、UNION/INTERSECT 等の集合演算子を構造的に確認できる。いずれかのチェックを満たさない SQL は実行前に棄却される。検証は以下の14のチェックから成る：

\begin{enumerate}[nosep]
  \item カラム存在確認（ホワイトリスト照合）
  \item テーブル存在確認（許可されたテーブル照合）
  \item FK整合性のあるJOIN確認
  \item マルチステートメント検出（セミコロン分割）
  \item DMLキーワード検出（DROP/DELETE/INSERT/UPDATE）
  \item SQLインジェクションパターン検出
  \item LIMIT句の存在確認（欠如時は自動追加）
  \item DISTINCT推奨（JOIN時）
  \item SELECT * 禁止
  \item サブクエリのネスト深さ制限
  \item UNION/INTERSECT句の検証
  \item 算術演算の型の有効性
  \item ORDER BY/GROUP BYの参照整合性
  \item エイリアス解決後のカラム参照確認
\end{enumerate}

SQLGuardの価値は、精度向上ではなく、実行前の安全性と整合性を保証することにある（セクション~\ref{sec:injection_safety}を参照）。

\subsection{ハイブリッドリランカー}

SQL候補のリランキングにはGPT-5.5を使用する。少数ショットの例選択にはクロスエンコーダー（ローカル、$<$50\,ms）を使用し、SQL候補とスキーマのスコアリングにはGPT-5.5（API）を使用し、ハイブリッドアーキテクチャを形成する。

リランカーは複数の SQL 候補を比較して最適な 1 本を選択する。中程度から Hard クラスのクエリでは正解候補を選び出す効果が期待される一方、全候補が部分的に誤っている VH クラスでは選択の難易度が高まる。

\subsubsection{日本語クロスエンコーダーの比較}

少数ショットの例選択に使用されるクロスエンコーダーについて、英語モデル（ms-marco-MiniLM-L-6-v2）と日本語モデル（hotchpotch/japanese-reranker-cross-encoder-xsmall-v1）を20のVery Hardクエリで比較した。英語モデルは32.4\%を達成し、日本語モデルは28.1\%であった（$-$4.4\,ppの差がms-marcoに有利）。少数ショットの例にはSQLコード（英語）が含まれているため、ms-marcoの英語スコアリング能力がその優位性に寄与している可能性がある。

\subsection{修復ループ}
\label{sec:repair}

SQL実行エラーや結果の有効性の問題が検出された場合、エラーメッセージがLLM（GPT-5.5）にフィードバックされ、最大3回の修復試行が行われる。  
\subsection{データベースと評価設計}
\label{sec:evaluation}  
\subsubsection{検証データベース}

提案された方法を検証するために、L1$_2$型金属間化合物を題材としつつ、無機材料データベース全体に共通する正規化スキーマを表す検証 RDB を構築した。L1$_2$ を代表例とするだけでなく、組成・構造・熱力学的安定性・電子構造・機械的特性・表面特性など、材料 RDB に普遍な概念を 31 の正規化テーブルと 1 つのビュー（図~\ref{fig:er}）に配置する。\texttt{material\_entry} を中心エンティティとし、FK 関係で周辺テーブルと接続する構成は、OQMD、Materials Project、AFLOW などの無機材料データベースと同じ設計パターンを持つ。主要な統計は表~\ref{tab:db_stats}に示されている。
\paragraph*{ソースOQMDスタイルデータレイアウトとの関係}

公開されているOQMDデータモデルは、少数の広いエントリ中心のテーブル（例：\texttt{entries}、\texttt{element\_ratios}、\texttt{formation\_energies}、\texttt{reference\_states}、および\texttt{elements}）で表現できる。このレイアウトは高スループットデータの蓄積に効率的だが、構造的に異なる情報（組成、結晶構造、熱的安定性、電子特性）を、\texttt{delta\_e}や\texttt{composition\_formula}のような一般的なカラムに格納している。自然言語インターフェースにおいて、これは曖昧さを引き起こす。「エネルギー」は生成エネルギー、ハル距離、またはバンドギャップを指す可能性がある。「Ti」は構成元素または特性フィルターのターゲットである可能性がある。

生成エンタルピーは、純元素の参照エネルギーと化合物の全エネルギーとの差として、多段階の共通テーブル式（CTE）で計算される。
本研究では、実在する無機材料データベースの構造を忠実に模倣した検証環境を構築した。データの信頼性を担保するため、純元素の参照エネルギーにはOQMDを用い、その他の特性についてはプログラムにより生成した合成データを使用している。これらを31の正規化テーブルに割り当てることで、実際のRDBに近い複雑なスキーマを実現した。この設計はタスクを簡略化するものではなく、むしろ難易度を高めるものである。評価用SQLは平均3.4、最大で6つのテーブル結合および多段階CTEを必要とする構成となっており、高度な操作が求められる。このようにデータベースの複雑さを明示的なスキーマとして定義することで、ユーザーの負担を軽減しつつ、結合処理などの複雑なタスクをText-to-SQLパイプラインへと集約させている。これらに対し、Steinerツリーを用いたJOIN生成器やスキーマリンク等の高度な手法を導入することで、正確な処理を実現した。

\subsubsection{評価クエリ}

私たちは100の著者設計のクエリを使用した（表~\ref{tab:query_design}）。各クエリには、ゴールドSQL、期待される実行結果（JSON）、必要なテーブル、およびJOINパスが注釈されている。無機材料RDB用の標準的なText-to-SQLベンチマークは現在存在しないため、データベーススキーマ構造と材料研究者の典型的な情報ニーズに基づいて評価クエリを構築した。クエリは以下の原則に従って設計された：
(1) 実際の材料研究で生じる質問をシミュレートする（例：安定相の検索、組成と特性の相関）、
(2) 難易度はゴールドSQLから計算された統一的な複雑性スコアによって4つの層に分類される（必要なテーブルごとに$3$ + WHERE/HAVING条件ごとに$1$ + GROUP BYごとに$2$ + EXISTSサブクエリごとに$3$ + 派生サブクエリごとに$3$；易しい $<8$、中程度 $8$--$11$、Hard $12$--$16$、非常に難しい $\geq 17$）、
(3) すべてのカテゴリ（A--H）にわたってバランスの取れたカバレッジ、
(4) 高度な分析パターンを評価するために5つのCTEマルチステップ計算クエリが含まれている。

クエリには「安定な」「エネルギー差の大きい」など、自然言語で一義的に解釈できないあいまいな表現も意図的に含まれている。これらに対する解釈は、辞書と少数ショット例で定めた対応付けに依存しており、問いを具体化するインターフェースがあれば、より多くの VH クエリを Easy に近づける余地がある。著者設計のクエリの制限として、クエリの分布が実際のユーザー使用パターンと異なる可能性がある；ユーザー研究は今後の検証タスクとして残る。

\subsubsection{評価指標}

行レベルの再現率が主要な指標として使用される。生成されたSQLとゴールドSQLの実行結果は共通の列に投影され、行レベルの一致率が計算される：
\begin{equation}
  \text{accuracy}(q) = \frac{|R_\text{gen}^{C} \cap R_\text{gold}^{C}|}{|R_\text{gold}^{C}|}
  \label{eq:column_aware}
\end{equation}
ここで、$C = \text{cols}(R_\text{gen}) \cap \text{cols}(R_\text{gold})$は共通の列セットであり、$R^C$は列セット$C$への投影を示す。この指標は再現率ベースである：生成されたSQLがゴールドよりも多くの行を返す場合、ペナルティは発生しない。評価中は、LIMIT 10{,}000がゴールドSQLと生成されたSQLの両方に均等に適用される。

\subsubsection{探索結果の解釈に関する注意事項}

\section{考察}
\label{sec:discussion}

\subsection{無機材料RDBにおけるスキーマの障壁と自然言語アクセスの重要性}

本研究の結果は、無機材料 RDB におけるデータ利用の主な障壁は SQL 文法そのものではなく、正規化されたスキーマ構造の理解にあることを再確認する。no\_fewshot（77.3\%）と no\_dict（77.4\%）のいずれも full（84.7\%）を大きく下回り（表~\ref{tab:ablation}）、特に VH 層ではそれぞれ48.3\%、37.1\%に低下する。少数ショット例と材料ドメイン辞書はどちらも不可欠である。

自然言語インターフェースは、このスキーマの障壁を効果的に低減できる。少数ショット例と材料ドメイン辞書の併用により、精度は84.7\%に回復し、特にドメイン特有の語彙を多く使用する複雑なクエリで顕著な向上が見られる。この改善は、無機材料RDBへの自然言語アクセスが単なる利便性を超え、スキーマの障壁により以前はアクセスできなかったデータへの実質的なアクセスを可能にすることを示唆している。具体的には、100\%の構文の有効性と100\%の実行成功を達成すること（表~\ref{tab:multiaxis}）は、SQLに不慣れな材料研究者が自然言語を通じて安全にデータベースを使用できることを意味する。93.2\%のJOINマッチ率は、正規化されたマルチテーブルRDBにおいてテーブル結合パスが高精度で特定されていることを示し、スキーマ理解の負担を大幅に軽減する。

スキーマの進化とデータの成長に関して、我々のパイプラインはFKメタデータベースの設計を採用しているため、テーブルの追加やFKの変更は自己反映される。辞書と少数ショット例の更新には手動の努力が必要だが、標準手順に減らすことができ（テーブル定義 $\to$ FK設定 $\to$ 辞書登録 $\to$ 少数ショット例追加）、運用維持コストを抑えることができる。

\subsection{少数ショット例の貢献}

少数ショット例を削除すると、すべてのコンポーネントの中で最大の精度低下が見られた（$-$7.4\,pp, $p<0.001$; 表~\ref{tab:ablation}）。この低下は、中程度の層以上で観察され、非常にHard層では$-$10.3\,ppの低下が見られた（表~\ref{tab:ablation-detail}）。次いで、Hard層で$-$8.5\,pp、中程度の層で$-$9.2\,ppの低下があり、より複雑なクエリが少数ショット例に対してより大きな依存を持つことを示している。少数ショット例なしでは、レイテンシも31.0\,sから50.7\,sに増加した（表~\ref{tab:latency}）。これは、LLMが試行錯誤を通じてSQLを生成するためと考えられる。

\subsection{材料ドメイン辞書の貢献}

辞書を削除すると、全体で$-$7.3\,ppの低下が見られた（$p<0.001$）。ただし、効果はHard層によって異なった（表~\ref{tab:ablation-detail}）。簡単な層では低下は見られなかったが、Hardクエリ層では$-$9.3\,pp、非常にHardでは$-$21.5\,ppの低下が見られた。

簡単および中程度のクエリは一般的な表現で構成されており、LLMは自らSQL条件を推測できる。対照的に、VH クエリは同時に複数のドメイン特有の用語を含み、辞書がないとLLMは正しいSQL条件を生成できない可能性がある（例：``$\gamma'$相'' $\to$ \texttt{structure.prototype = 'L12'}）。

\subsection{リランカーの貢献}
\label{sec:reranker_discussion}

リランカーを削除すると、$-$3.3\,ppの低下が見られた（$p=0.364$、統計的に有意ではない）。この効果は、中程度（$-$6.7\,pp）およびHard層（$-$5.6\,pp）で観察された（表~\ref{tab:ablation-detail}）。

しかし、非常にHard層では、リランカーを削除した際に$+$3.1\,ppの精度向上が見られた。この差は標準偏差の範囲内（VH層SD = 2.2\,pp）だが、リランカーは非常にHard層では実際には逆効果を持つ可能性がある。この層では、すべての候補が部分的に不正確であることが多く、リランカーは「より正しく見えるが実際には間違っている」候補を選択する可能性がある。特にCTEクエリでは、構文的には有効だが意味的には不正確な候補が高いリランカーのスコアを得ることがある。対照的に、中程度およびHardでは、少なくとも1つの正確な候補が存在することが多く、リランカーはそれを正しく選択できる。これらの結果は、リランカーの効果がクエリの複雑さに依存しており、高複雑度クエリに対するリランク戦略の改善の余地があることを示唆している。

\subsection{SQLGuard、$n$-best、およびシュタイナー木の貢献}

SQLGuard（$-$0.2\,pp、n.s.）、$n$-best（$-$0.6\,pp、n.s.）、およびシュタイナー木（$+$0.0\,pp、n.s.）は、生の実行精度では統計的に有意な効果を示さなかった。ただし、n.s.\ は ``意味がない''ことを意味するわけではない。

SQLGuardの主な役割は安全性の安全網であり、SQL インジェクションや非 SELECT 文を排除して構文妥当率を 100\%に保つ。アブレーションでは精度効果は小さいが、これはリランカーがすでに多くの危険な候補を低スコアにしているためで、セキュリティ層としての価値は独立して存在する。

$n$-best = 1に設定すると、精度を維持しつつレイテンシを31.0\,sから10.9\,sに短縮できる（表~\ref{tab:latency}）。これはコスト効率が優先される場合に有効な選択肢となる。

シュタイナー木は実行精度に大きな変化を与えなかったが、JOIN幻覚を半減させる（シュタイナー木なしで6、ありで3；表~\ref{tab:error_analysis}）。その主な役割は生の精度ではなく JOIN パスの健全性にある。FK イントロスペクションに基づく設計のため、テーブル数の増加や他の正規化 RDB（Materials Project~\cite{jain2013mp}、AFLOW~\cite{curtarolo2012aflow}）への適用で利点が明らかになることが期待される。

\subsection{アブレーション条件の定量的比較}

アブレーション条件は、1つのコンポーネントを除いた簡略化された手法として見ることができる（表~\ref{tab:ablation}）。no\_fewshot条件は、辞書とリランカーを保持しながら少数ショットの例のみを除去し、77.3\% ($-$7.4\,pp)の精度を得る。また、no\_dict条件は辞書のみを除去し、77.4\% ($-$7.3\,pp)の精度を得る。これらは2つの最大の単一コンポーネントの低下であり、ほぼ同一であることから、少数ショットの例と辞書が全体の精度に対する2つの主要な寄与者であることを示している。提案された完全な手法は84.7\%に達する。

アブレーションは1つのコンポーネントを一度に除去するため、明らかな段階的値は真の増分追加実験ではない。コンポーネント間の相互作用により、寄与は厳密に加算的ではない。同じデータベース上で他の手法（DIN-SQL、DAIL-SQLなど）との直接比較は行われていない（制限事項~6を参照）。LLMのみおよびスキーマのみ（少数ショットの例なし）構成の質的SQL例は、補足セクション~\ref{sec:sup_sql_examples}に提供されている。

\subsection{多段階計算クエリの処理}
\label{sec:multistep_query}

無機材料RDBへの自然言語アクセスにおける要件は、派生量計算を伴う多段階データ抽出である。代表的なケースとして、クエリ``Ni$_3$Alの生成エンタルピーを純元素参照を用いて計算せよ''を考える。このクエリに正しく答えるためには、以下の多段階データ抽出と計算が必要である：
\begin{enumerate}
  \item \texttt{phase\_stability}テーブルから化合物Ni$_3$Alの生成エネルギー$E_\mathrm{f}$を取得する。
  \item \texttt{composition}テーブルから構成元素NiとAlの組成比$x_i$を取得する。
  \item \texttt{pure\_element\_reference}テーブルから各元素の基底状態エネルギー$E_\mathrm{ref}(i)$を取得する（OQMD由来、89元素）。
  \item 加重参照エネルギー$\sum_i x_i E_\mathrm{ref}(i)$を計算する。
  \item 修正された生成エンタルピー$\Delta H_\mathrm{f} = E_\mathrm{f} - \sum_i x_i E_\mathrm{ref}(i)$を出力する。
\end{enumerate}

この操作は単一テーブルのルックアップではなく、3テーブルのJOIN、サブクエリによる集計計算、および算術演算を含むCTE（共通テーブル式）としてSQLに変換する必要がある。我々のパイプラインは、LLMが\texttt{formation\_enthalpy}ビューを介して単純なクエリを生成し、対応する少数ショットの例を追加することで明示的なCTEベースの計算を行うことを可能にする。

従来のテキストからSQLへのベンチマーク（Spider~\cite{yu2018spider}、BIRD~\cite{li2024bird}など）は、主にSELECT--WHERE--JOIN--GROUP BYの組み合わせをカバーしており、科学計算に不可欠な多段階データ統合および派生量計算を必要とするクエリは含まれていない。材料データベースにおいて、生成エンタルピー、体積サイズ因子、格子不整合などの派生量は研究上重要であり、そのような計算を自然言語で直接指示できる能力は、材料情報学における自然言語インターフェースの実用性を大幅に向上させる。  
\subsection{独立に設計されたクエリによる評価}
\label{sec:independent_eval}

自己参照バイアスを検証するために、パイプラインの実装には関与していない共同著者の末松知恵によって独立に設計された100のクエリを使用して精度を再評価した。これらのクエリは、クエリ設計と独立評価に貢献した（簡単18 / 中程度34 / Hard 34 / 非常に難しい14）、10のカテゴリ（基本検索、構成/要素、構造/格子定数、安定性/形成エネルギー、DFT計算/特性、電子構造/磁気/熱特性、表面/粒界/欠陥、文献/合成/応用、材料設計/スクリーニング、比較/統計）にわたっている。これらのクエリは、アブレーション研究で使用されたのと同じ連続実行リコールメトリックと難易度分類でスコアリングされた。

全体の実行精度は76.9\%（簡単94.4\% / 中程度81.7\% / Hard 61.5\% / 非常に難しい80.4\%）で、著者設計のセット（84.7\%; 表~\ref{tab:ablation}）よりも7.8\,pp低い。このギャップは主に3つの要因に起因している。

(1) テーブルカバレッジバイアス（主な要因）：
著者設計のゴールドSQLはコアテーブルのセットを使用しているが、独立に設計されたクエリは、\texttt{elastic\_tensor}、\texttt{magnetic\_property}、および\texttt{surface\_energy}などの追加テーブルを参照しており、少数ショットの例がまばらである。

(2) 少数ショット最適化バイアス：
ほとんどの著者設計のクエリは、固定パターンとして「L1$_2$」を明示的に含んでおり、少数ショットの例はこのパターンに最適化されている。独立に設計されたクエリは、より多様な表現を使用している。

(3) 語彙の多様性：
独立に設計されたクエリは、現在のパイプラインが明示的なキーワードマッチングに依存しているため、Hard 暗黙の条件指定を頻繁に使用する。

構文の有効性（100.0\%）は両方のセットで一貫しており、スキーマグラフ制約のクエリ起源の独立性を確認している。非常にHard層（80.4\%）はHard層（61.5\%）よりも高いのは、14の非常に難しいクエリが少数ショットの例でカバーされているいくつかの短いCTEパターンを含んでいるのに対し、いくつかの難しいクエリは少数ショットのサポートなしに周辺テーブルを参照しているためである。詳細な結果は補足資料~\ref{sec:sup_expert_queries}に提供されている。

\subsection{列間比較クエリの取り扱い}
\label{sec:column_comparison}

多段階計算に加えて、列間比較は材料研究で頻繁に遭遇する代表的なクエリパターンである。「値Aが値Bより小さいエントリを見つける」という形式のクエリは、同じ行内の異なる列の値を比較する条件式を用いたSQL生成を必要とするため、単一の閾値フィルタリング（\texttt{WHERE col > 0.5}）とは異なる（\texttt{WHERE col\_a > col\_b}）。

私たちのパイプラインは、3種類の列間比較パターンをカバーする少数ショットの例を提供する。  
\begin{enumerate}  
  \item テーブル内比較：  
    同じテーブル内の2つの列の直接比較。  
    例：\texttt{formation\_energy\_per\_atom < energy\_above\_hull}（\texttt{phase\_stability}テーブル内）；  
    \texttt{bulk\_modulus\_vrh > 2.0 * shear\_modulus\_vrh}（\texttt{elastic\_tensor}テーブル内、Pugh延性メトリック）。  
  \item テーブル間比較：  
    JOINを介して異なるテーブルの列を比較。  
    例：\texttt{thermal\_property.debye\_temperature\_k > magnetic\_property.curie\_temperature\_k}；  
    総磁化対絶対形成エネルギー。  
  \item 集約関数を用いた比較：  
    GROUP BY--HAVINGと組み合わせて、構成要素間の電気陰性度差などの導出量に対する閾値評価を行う。  
    例：\texttt{HAVING MAX(electronegativity) - MIN(electronegativity) > 0.5}。  
\end{enumerate}

これらのパターンは、定数比較（\texttt{WHERE col > 0.5}）に比べてLLMが正しく生成するのが難しい。特にテーブル間比較は、スキーマ情報から各比較列がどのテーブルに属するかを正確に特定する必要がある。私たちは、主に列間比較パターンを追加して少数ショットの例プールを45例に拡張し、LLMがそのようなパターンを学習できるようにした。

\subsection{RDBスキーマ設計とText-to-SQLコスト}
\label{sec:schema_design_cost}

この研究を通じて得られた洞察は、RDB自体のテーブル構造がText-to-SQL精度を決定する上流要因であるということである。

高度に正規化されたスキーマでは、単一のクエリに対して複数のテーブルJOINが必要であり、LLMが生成しなければならないSQLの複雑さが増す。私たちのデータベースにおける形成エンタルピー計算（セクション~\ref{sec:multistep_query}）では、\texttt{phase\_stability}、\texttt{composition}、および\texttt{pure\_element\_reference}の3テーブルJOINが必要であり、さらにCTEベースの集約計算が必要であった。少数ショットの例なしでの精度の$-$7.4\,ppの低下は、より複雑なテーブル間結合パターンがLLMによる正確なSQL生成をより困難にすることを確認している。

この洞察に基づいて、T2SQL準備のための以下のスキーマ設計戦略を考慮できる：
\begin{enumerate}
  \item ビューによる複雑さの隠蔽：
    よく使用される多段階JOINパターンをビューまたはマテリアライズドビューとして定義し、LLMに対して単一のSELECTでクエリ可能なインターフェースを提供する。この研究における\texttt{formation\_enthalpy}ビューがその例である。
  \item クエリ頻度に基づく非正規化：
    よく参照されるテーブルグループ（例：\texttt{composition}と\texttt{element}）を事前に結合されたテーブルとして提供し、JOINの数を減らす。
  \item 自己記述的な列名付け：
    列名にテーブルのコンテキストを埋め込み（例：\texttt{energy} $\to$ \texttt{formation\_energy\_per\_atom}）、LLMがスキーマ情報から適切な列を選択する確率を高める。
  \item 明示的なFK制約定義：
    スタインナー木アルゴリズムはFK関係に基づいて最小JOINパスを決定する。自動JOIN解決はFK制約が欠如しているスキーマでは失敗する。T2SQL準備が設計目標である場合、包括的なFK制約の定義が必要である。
\end{enumerate}

要約すると、Text-to-SQLシステムの精度を向上させるには、パイプライン側の改善だけでなく、データベーススキーマ設計段階でのNLインターフェースの互換性を考慮する必要がある。この視点は、この研究で使用された検証DBだけでなく、類似の正規化スキーマを持つ無機材料RDB（OQMD、Materials Project、AFLOWなど）や、Text-to-SQLが適用されるドメイン特化型RDBに一般的に適用可能な設計ガイドラインとして機能する。
\subsection{CTEマルチステップ計算クエリの評価}
\label{sec:cte_evaluation}

CTE（共通テーブル式）を用いたマルチステップ計算クエリの能力を定量的に評価するために、形成エンタルピー計算を例として、5つの非常にHardクエリ層をCTEクエリに置き換え、評価を実施した。これらの5つのクエリは以下のカテゴリをカバーしている。

\begin{enumerate}[nosep]
  \item シンプルCTE（導出量計算）:
    特定の化合物の$\Delta H_f$を純元素参照を用いて計算する
  \item CTE + フィルター:
    安定したL1$_2$化合物の$\Delta H_f$を計算し、閾値でフィルタリングする
  \item CTE + 集約:
    Aサイト元素ごとの平均$\Delta H_f$を集約する
  \item マルチステージCTE（2段階以上）:
    3段階CTE: 安定性フィルター $\to$ $\Delta H_f$計算 $\to$ 元素フィルター

CTEサポートの適用限界を定量化するために、10の新しいパターン（ウィンドウ関数、HAVINGフィルター、2段階集約、弾性/熱/磁気テーブルへのJOIN、条件付き集約、3段階CTEなど）を追加し、合計15のクエリを評価した。少数ショット例でカバーされた5つの元のパターンは100\%を維持したが、10の新しいゼロショットパターンはわずか42.3\%に達し、全体で61.6\%となった。この結果は、アブレーションで観察された少数ショットの大きな寄与（$-$7.4\,pp, $p<0.001$）と一致しており、マルチステップ計算サポートの範囲は少数ショット例のパターンカバレッジによって制御されていることを示している。したがって、新しいマルチステップパターンへの拡張は、ドメイン専門家によって追加された少数の例（パターンごとに約1つ）を通じて達成可能であり、モデルの再トレーニングなしに実現できるというこの設計の実用的な利点である。

\subsection{類似無機材料RDBへの拡張性}
\label{sec:extensibility}

本研究で得られた設計原則は、検証に使用された特定のデータベースに限定されない。FKイントロスペクションに基づくシュタイナー木アルゴリズムは、テーブルの追加やスキーマの変更を必要とせず、定義されたFK制約を持つ任意の正規化されたRDBで動作する。ドメイン辞書については、新しい材料システム（ヘウスラー、ペロブスカイトなど）や異なるデータベースに適用する際に語彙の追加が必要だが、辞書の構造自体（4つのカテゴリ：プロトタイプエイリアス、元素マッピング、安定性用語、特性用語）は一般的に無機材料RDBに適用可能である。

しかし、以下の注意点に留意する必要がある。本研究の主な評価は単一のOQMD由来のデータベースに基づいている；セクション~\ref{sec:transfer_eval}ではスキーマの名前変更、難読化、プロトタイプの拡張、実際のMaterials Project風スキーマへの一般化が示されたが、根本的に異なる意味論を持つRDBや、はるかに大規模なRDBへの一般化性能を主張するものではない。少数ショットの例は検証DBスキーマに依存しており、異なるRDBに適用する際にはドメイン専門家による新しい例の設計が不可欠である。これらの制限を考慮に入れた上で、本研究は無機材料RDBへのNLアクセスのための設計原則の一つのデモンストレーションを提供する。

\subsection{制限事項と今後の研究}

\begin{enumerate}
  \item 単一データベースの検証:
    本研究の主な評価はOQMD由来のL1$_2$データベース（31テーブル、1ビュー、1{,}559エントリ）に基づく。ゼロ適応転送テスト（セクション~\ref{sec:transfer_eval}）では、スキーマの名前変更（90.5\%）、難読化された識別子（90.0\%）、プロトタイプの拡張（90.0\%）、および実際のMaterials Project風スキーマ（100.0\%）への一般化が示されたが、根本的に異なる意味論やスケールを持つRDBへの一般化は確認されていない。
  \item 31テーブル・1ビュー構成の限界:
    あくまで検証環境であり、スキーマサイズは現実の材料RDBより小さい。1つの代表スキーマに基づくため、属性名の多様さ（同義語、略語、複数言語）や異なる正規化方針を網羅しているわけではない。スキーマメタデータだけでは解決できない暗黙知（例：特定の材料体系における「安定」の意味）が残る。
  \item 統計テストの範囲:
    ウィルコクソン符号付き順位検定が、5回の実行にわたって完全条件に対するクエリごとの精度差（$n=100$）に対して実施された。実行回数は限られており、複数比較の補正は適用されていない；ブートストラップや他の方法は、より正確な信頼区間のために有用である。
  \item クエリのカバレッジ:
    100の著者設計のクエリは、材料研究における主要な検索パターンをカバーするように設計されているが、実際の使用で遭遇する多様なクエリパターンを網羅的にカバーしているわけではない。
  \item ゴールドSQLの検証:
    ゴールドSQLと期待される結果は著者によって作成された；独立に設計された100クエリセットは、共同著者の末松知恵によってクロスチェックされたが、外部研究者による完全な独立第三者検証は行われていない。
  \item 辞書のカバレッジ:
    492用語の辞書はL1$_2$探索に特化している；ヘウスラー、ペロブスカイト、その他のシステムへの拡張には手動登録が必要である。スキーマメタデータからの半自動生成への移行が望まれる。
  \item あいまいな自然言語表現への対処:
    「安定な」「エネルギー差の大きい」など、自然言語のあいまいな表現に対する正当な解釈は一義的ではない。単語の一致や辞書の対応だけでは、文脈に依存する比較対象や閾値を決定できない場合がある。評価セットとは別に、実際のユーザーが投入し得るあいまい・矛盾クエリの例として次のようなものが挙げられる：(i)~「NiAl の組成比で L1$_2$ 構造のものを出してほしい」（NiAl は 1:1 組成の B2 型であり、1:3 組成の L1$_2$ とは前提が矛盾する）、(ii)~「安定な化合物を出して」（凸包距離か生成エンタルピーの符号か、基準が未指定）、(iii)~「生成エンタルピーが 0.5\,eV より大きい安定化合物」（安定性は負の生成エンタルピーを意味するため閾値と矛盾する）、(iv)~「融点が 2{,}000\,K 以上の L1$_2$ 化合物」（スキーマに存在しない属性への問い）、(v)~「$\gamma$ 相の合金を出して」（鉄鋼の $\gamma$（fcc）か Ni 基超合金の $\gamma'$ かが不明な多義語）、(vi)~「一番多い元素は？」（材料数ベースか組成比ベースかの集計単位が不明）、(vii)~「D0$_{19}$ 構造の化合物」（検証データベースに存在しないプロトタイプ）。これらは条件の欠落・矛盾・スキーマ外参照という異なる失敗様式を代表する。問いを具体化するインターフェース（対象の元素、閾値、比較軸を対話的に確定させ、矛盾や欠落を指摘する機構）を併用すれば、Very Hard クエリを Easy に近づける余地がある。
  \item 使用言語への依存性:
    本研究の評価クエリは日本語であるが、パイプラインの中核設計（LLM による SQL 生成、スキーマリンク、few-shot 検索、Steiner 木 JOIN 生成）は言語に依存しない。ただし、MeCab によるトークン化やドメイン辞書のように言語に依存する構成要素もあるため、英語等のクエリに適用するにはトークナイザ・辞書・few-shot 例を対象言語向けに整備する必要がある（本研究では英語クエリでの系統的検証は行っていない）。
  \item ベースラインの公平性:
    同じデータベースに対する他の手法（DIN-SQL、DAIL-SQLなど）との直接比較は行われていない。
\end{enumerate}

\subsection{今後の展望}

\begin{enumerate}
  \item 他の無機材料RDBでの検証:
    Materials ProjectやAFLOWなど、異なるスキーマを持つ無機材料RDBへの適用を通じて設計原則の一般性を検証する。
  \item 大規模データの検証:
    OQMDの単一元素データを統合することで、10{,}000エントリ規模でのシュタイナー木探索とSQL生成の精度を検証する。
  \item 拡張CTE評価:
    本研究では5つのCTEクエリで100\%の精度が確認された（セクション~\ref{sec:cte_evaluation}）；より多様な導出量パターン（相安定性図、弾性異方性メトリクスなど）への評価を拡張する。
  \item AI4Sエージェントの統合:
    MCPプロトコルまたは関数呼び出しを介して、自律材料探索エージェントのツールとしてT2SQLメソッドを組み込む。
  \item CALPHADの統合:
    スキーマグラフのトラバーサルによってRDBから候補を絞り込み、その後温度依存の相安定性評価のためにCALPHAD自由エネルギー計算を行う二段階のフローである。
  \item 多軸評価指標:
    SELECT列の精度、JOINパスの一致率、Top-$k$精度などを別々に評価し、エラーの原因特定を促進する。
  \item 問いの具体化インターフェース:
    自然言語のあいまい表現を対話で確定させる仕組みを組み合わせ、VH層の扱いを容易にする。
\end{enumerate}
\section{結論}\label{sec:conclusion}

本研究は、無機材料 RDB への自然言語アクセスを実現する Text-to-SQL パイプラインの設計原理を提示し、その有効性を 31 テーブルの L1$_2$ 原型 RDB を用いて実証した。

7 条件 $\times$ 100 クエリ $\times$ 5 回実行の ablation study（計 3{,}500 件評価）から、材料ドメイン辞書（$-$7.3\,pp, $p<0.001$）と少数ショット例（$-$7.4\,pp, $p<0.001$）が材料特有のクエリパターンに不可欠であることが示された。多元素条件、化合物特性検索、ドメイン用語を含む問いにおいて改善が顕著であった。一方、JOIN パスの誤りは少なく、残る主要な失敗モードは WHERE 句条件の組み合わせ誤りである（セクション~\ref{sec:error_analysis}）。

実行再現率 84.7\%, 適合率 77.3\%, F1 74.8\%, 構文妥当率 100\%, JOIN 一致率 93.2\% という多軸評価は、提案パイプラインが精度だけでなく安全性と結合経路の正確性を両立することを示す。なかでも SQLGuard は非 SELECT 文を排除し、構文妥当率を 100\% に保つことで、実用上の安全要件を満たす。4 種類のゼロ適応転用試験（A~90.0\%, B~90.5\%, C~90.0\%, D~100.0\%）により、FK イントロスペクションに基づく設計が特定のスキーマに依存しないことも示した。純元素基準からの生成エンタルピー計算を含む 15 パターンの CTE 多段計算は、単なる情報検索を超えた導出計算の実現可能性を示した。独立設計 100 件の外部検証（76.9\%）も含め、SQL を記述しない材料研究者がクロステーブル探索・工学的問いかけを行うための実用的な土台ができた。

これらの結果は、無機材料 RDB におけるデータ利用の主な障壁が SQL 文法そのものではなく、正規化されたスキーマ構造の理解にあることを再確認する。示された精度は ablation 条件や難易度ティアによって大きく変動するため、どの組み合わせの機能がどの難易度の問いに寄与するかを開示し、ユーザが適切なクエリを投入できるように誘導することで、材料研究者にとって高く安全な NL-to-SQL 環境が実現できる。

本研究は、自然言語を介した材料データベースアクセスという AI for Science（AI4S）における実用的な基盤を示す。大規模言語モデル（LLM）を科学データの前線に配置する際、単に生成AIを活用するのではなく、スキーマグラフ、ドメイン辞書、SQLGuard、リランカーなどの制約機構を組み合わせることで、科学データの関係性を正しく扱いながら安全に利用できることを示した。材料研究者が SQL やスキーマ構造を意識せずにクロステーブル探索・多段階導出計算を行えるようになることは、実験・シミュレーションを橋渡しするデータ駆動型材料科学の一翼を担う。また、本パイプラインは既存の材料 RDB インフラ（MInt~\cite{minamoto2020mint}、pinax~\cite{minamoto2026pinax} 等）に対し、新たなデータ変換や移行を強いることなく自然言語インターフェースを付加可能であり、AI4S エージェントの信頼性の高いツールとして展開できる。未来的には、問いの具体化インターフェースや CALPHAD 計算等との連携により、自律的な材料探索ループの構成要素となることが期待される。

\section{生成されたSQLの例}
\label{sec:sup_sql_examples}

代表的なクエリに対する生成されたSQLの例を、3つのメソッド構成（LLMのみ、フルスキーマ、我々の方法）で比較する。これは、各構成における出力SQLの質的な違いを具体的に示すことで、表~\ref{tab:ablation}における定量的比較を補完する。

\subsection{``Niを含む安定なL1$_2$化合物のリスト''}

\paragraph{LLMのみ（スキーマなし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT formula, stability
FROM materials
WHERE element = 'Ni'
  AND structure_type = 'L12'
  AND stability = 'stable';
-- テーブルの幻影: materials, stability などは存在しない
-- 実行不可（ERROR: relation "materials" does not exist）
\end{lstlisting}

\paragraph{フルスキーマ（プロンプト内にスキーマ、少数ショット例なし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT m.formula, ps.is_stable
FROM material_entry m
  JOIN composition c ON c.entry_id = m.entry_id
  JOIN structure s ON s.entry_id = m.entry_id
  JOIN phase_stability ps ON ps.entry_id = m.entry_id
WHERE c.element = 'Ni'
  AND s.strukturbericht = 'L12'
  AND ps.is_stable = true;
-- 実行可能だが不完全:
-- (1) プロトタイプ条件なし（L12がstrukturberichtにない場合を見逃す）
-- (2) DISTINCT/LIMITなし
-- (3) lattice_aのような実質的に有用な列を選択しない
\end{lstlisting}

\paragraph{我々の方法（スキーマグラフ + 少数ショット + 辞書）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT DISTINCT m.entry_id, m.formula,
  s.prototype, s.lattice_a, s.space_group
FROM material_entry m
  JOIN composition c ON c.entry_id = m.entry_id
  JOIN structure s ON s.entry_id = m.entry_id
  JOIN phase_stability ps ON ps.entry_id = m.entry_id
WHERE (s.prototype = 'L12'
    OR s.strukturbericht = 'L12')
  AND c.element = 'Ni'
  AND ps.energy_above_hull <= 0.001
LIMIT 10000;
-- スキーマグラフのトラバースにより3つのJOINのみ必要
-- テーブルの幻影なし、DISTINCTとLIMITを含む
\end{lstlisting}

\subsection{``NiとAlの両方を含むL1$_2$化合物のリスト''}

\paragraph{LLMのみ（スキーマなし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT * FROM compounds
WHERE elements LIKE '%Ni%' AND elements LIKE '%Al%'
  AND crystal_structure = 'L12';
-- テーブルの幻影: compounds, elements列は存在しない
\end{lstlisting}

\paragraph{フルスキーマ（少数ショット例なし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT m.entry_id, m.formula
FROM material_entry m
  JOIN composition c ON c.entry_id = m.entry_id
  JOIN structure s ON s.entry_id = m.entry_id
WHERE c.element = 'Ni' AND c.element = 'Al'
  AND s.prototype = 'L12';
-- 致命的: 単一の行が両方の条件を同時に満たすことはできない -> 常に0行
\end{lstlisting}

\paragraph{我々の方法（EXISTSサブクエリ）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT DISTINCT m.entry_id, m.formula
FROM material_entry m
  JOIN structure s ON s.entry_id = m.entry_id
WHERE (s.prototype = 'L12'
    OR s.strukturbericht = 'L12')
AND EXISTS (
  SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Ni')
AND EXISTS (
  SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Al')
LIMIT 10000;
-- EXISTSサブクエリによる正確な多元素AND
\end{lstlisting}

\begin{enumerate}

\end{enumerate}

GPT-5シリーズAPIは温度パラメータをサポートしておらず、私たちの実装でも送信していない。その結果、出力はLLMの内部状態により同一の入力に対して異なる場合がある。本論文のすべてのアブレーション結果は、5回の独立した実行からの平均$\pm$標準偏差として報告され、統計的有意性はウィルコクソン符号付き順位検定によって確認されている。
