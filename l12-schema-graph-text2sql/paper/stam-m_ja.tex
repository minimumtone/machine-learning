\begin{abstract}
無機材料データベースはSQLの知識を前提としており、材料研究者にとってデータ活用の大きな障壁となっている。
本研究では、この障壁を取り除くため、無機材料向けリレーショナルデータベース（RDB）の自然言語アクセスを実現するText-to-SQLパイプラインの設計原理を提示し、その有効性を実証する。
提案手法は、(i) few-shot例検索、(ii) 大規模言語モデルによるSQL生成、(iii) 外部キーグラフに基づくSteiner木JOIN制約、(iv) 材料ドメイン辞書、(v) 抽象構文木解析ベースのSQL安全性検証（SQLGuard）、(vi) LLMリランカーの6要素から構成される。

L1$_2$型金属間化合物を中心とする31テーブル・数万レコードのRDBに対し、100件の評価クエリを用いて7条件のablation studyを5独立ランで実施した。
few-shot例と材料ドメイン辞書はそれぞれ$-$7.4\,pp（$p<0.001$）、$-$7.3\,pp（$p<0.001$）と統計的に有意な精度向上を示した。
多軸評価では実行再現率84.7\%、適合率77.3\%、F1値74.8\%、構文妥当率100\%、JOIN一致率93.2\%を達成した。

また、本稿では実行精度にとどまらず、材料RDBへの実用化に不可欠な3つの性質を確認した。
SQLGuardは任意の非SELECT文を排除し、構文妥当率を100\%に保つことで\textbf{安全性}を担保する。
プロトタイプ拡張（A）90.0\%、OQMD風命名変更（B）90.5\%、ランダム化名前転用（C）90.0\%、実在するMaterials Project風スキーマ（D）100.0\%の4種類のゼロ適応転用試験に成功し、\textbf{スキーマ非依存の汎化性}を示した。
さらに、純物質基準からの生成エンタルピー計算を含む15パターンのCTE多段計算により、単なる情報検索を超えた\textbf{導出計算の可能性}を実証した。
独立設計100件の外部検証（76.9\%）も合わせて、材料研究者がSQLを記述しなくてもクロステーブル探索・工学的問いかけができる研究インフラの実現を示した。
\end{abstract}

\section{はじめに}
\label{sec:introduction}

\subsection{無機材料研究におけるデータ探索の障壁}

無機材料研究は、高スループットの第一原理計算の進展により、データ駆動型の材料発見へと移行しています。
OQMD~\cite{saal2013oqmd,kirklin2015oqmd}、Materials Project~\cite{jain2013mp}、AFLOW~\cite{curtarolo2012aflow}、およびNOMAD~\cite{draxl2019nomad}のようなデータベースは、組成、結晶構造、電子状態、熱力学的安定性をカバーする数万から数十万の計算記録を保存しています。

これらのデータは通常、SQLを介した柔軟なクロステーブルクエリのために設計された正規化されたリレーショナルデータベース（RDB）に保存されます。
しかし、RDBを利用するには、テーブル構造、外部キー（FK）関係、およびSQL構文を理解する必要があり、関連するデータが存在することを知っていてもアクセスできない材料研究者にとっては大きな障壁となります。
その結果、研究者が自然言語でクエリを実行できないため、貴重なデータが十分に活用されていません。

\subsection{自然言語データベースインターフェースの重要性}

この障壁の核心は、SQL記述の技術的要件がドメイン知識とデータの間に介在していることです。
自然言語インターフェースは、SQLの代替となる便利なツールではなく、データアクセスの障壁を根本的に減少させ、研究を加速することができる研究インフラの一部です。

無機材料のRDBでは、正規化により数十のテーブルが生成され、複数のテーブルを含むJOINを構築することは、経験豊富なSQLユーザーにとっても困難です。
自然言語から適切なSQLが自動的に生成できれば、材料研究者はスキーマ構造を意識することなくクロステーブルデータ探索を行うことができます。

スキーマの変更やテーブルの追加を完全に自動で追跡するシステムを構築することは現在困難ですが、FKメタデータに依存する設計を採用することで、スキーマの進化への適応が比較的容易になります。

\subsection{Text-to-SQL技術と材料科学における現状}

Text-to-SQL技術は、Spider~\cite{yu2018spider}やBIRD~\cite{li2024bird}のようなベンチマークを中心に発展してきました。
最近の大規模言語モデル（LLM）の進展に伴い、DIN-SQL~\cite{pourreza2024dinsql}はスキーマリンク、分類、生成を分離したパイプラインアプローチを提案しました。
DAIL-SQL~\cite{gao2023dail}は、少数ショットの例選択戦略に焦点を当てました。
RAT-SQL~\cite{wang2020ratsql}は関係認識エンコーディングを導入し、RESDSQL~\cite{li2023resdsql}はスキーマリンクのデカップリングを導入しました。
SchemaGraphSQL~\cite{safdarian2026schemagraphsql}は、FKグラフ上のパス探索を使用している点で、我々の研究に最も近いです。

しかし、これらの方法は一般的なベンチマークで評価されており、特に無機材料データベースのドメイン特化型RDBには適用されていません。
材料データベースの自然言語インターフェースに関する研究は限られています。
MatSciBERT~\cite{gupta2022matscibert}やMatBERT~\cite{walker2021matbert}は材料科学テキスト用の言語モデルですが、Text-to-SQLタスクに直接適用されていません。
MKNA~\cite{zhuang2026mkna}やOptiMat~\cite{hu2026optimat}はAPIベースのアクセスを提供しますが、正規化されたRDBに対してJOIN制御を伴うSQL生成を行いません。
SuperCon~\cite{ishii2023supercon}やPoLyInfo~\cite{ishii2024polyinfo}は強力な意味論的推論を伴うRDF/SPARQLベースのオントロジーアプローチを採用していますが、既存のRDBインフラに適用するためにはデータ変換が必要です。

\subsection{目的と貢献}

本研究の目的は、無機材料RDBへの自然言語アクセスを可能にする設計原則を提示し、その有効性を検証することです。
我々は、材料研究者がSQLやスキーマ構造を意識することなくデータを探索できる方法論を示し、OQMDを代表的な例として自然言語クエリがどの程度処理できるかを検討します。

本研究で扱う3つのドメイン特有の課題は次のとおりです：
\begin{enumerate}
  \item \textbf{ドメイン用語の曖昧さ}：
    結晶構造名やL1$_2$、$\gamma'$相、B2のような特性用語は、一般的なLLMのトレーニングデータに十分に表現されておらず、SQL条件への正確な変換が困難です。
  \item \textbf{複数テーブルJOINの複雑さ}：
    正規化された材料RDBは数十のテーブル間でJOINを必要とし、LLMによるJOINの幻覚のリスクが高まります。
  \item \textbf{評価データの欠如}：
    無機材料RDBにおけるText-to-SQLのための標準評価ベンチマークは存在しません。
\end{enumerate}

我々の貢献は4つあります：
\begin{enumerate}[label=(\roman*)]
  \item \textbf{材料RDB Text-to-SQLのための設計原則}：
    我々は、FKグラフ上のSteiner-tree JOIN制約、材料ドメイン辞書、およびハイブリッド再ランクを統合したパイプラインを提案します。
    これは、材料特有の用語翻訳が欠如している一般的なText-to-SQL手法（DIN-SQL、DAIL-SQL、SchemaGraphSQLなど）と、RDB/SQLを対象としない材料NLアクセスシステム（MKNA、OptiMatなど）とのギャップを埋めます。
  \item \textbf{多軸定量評価}：
    31テーブルのL1$_2$ RDBに対する7条件$\times$100クエリ$\times$5回の統計的アブレーション（ウィルコクソン符号付き順位検定）を超えて、少数ショットの$k$感度、辞書サイズ感度、LLMモデル比較、および多軸メトリクス（EM / SELECT列精度 / JOIN一致率）を提供します。
  \item \textbf{ドメイン知識の定量的効果}：
    材料辞書（$-$7.3\,pp, $p<0.001$）と少数ショット例（$-$7.4\,pp, $p<0.001$）が統計的に有意な寄与を持つことを示し、ドメイン特化型モジュールの必要性を検証します。
  \item \textbf{スキーマ一般化のデモンストレーション}：
    四つのスキーマバリアントにわたるゼロ適応転送テスト---A~プロトタイプ拡張（90.0\%）、B~OQMD風の名前変更（90.5\%）、C~ランダム化された難読化（90.0\%）、およびD~Materials Project風のスキーマ（100.0\%）---は、FKイントロスペクションに基づく設計原則が特定のスキーマに依存しないことを示しています（セクション~\ref{sec:transfer_eval}）。
\end{enumerate}

\subsection{少数ショット例の検索}
\label{sec:fewshot}

入力クエリに類似した少数ショット例は、2段階で選択されます。
まず、TF-IDF~\cite{salton1988tfidf}が候補を$2k$アイテムに絞り込み、
次にクロスエンコーダ（ms-marco-MiniLM-L-6-v2）が上位$k$を選択します。
クロスエンコーダはローカルで実行され、処理時間は50\,ms未満です。

アブレーションスタディでは、少数ショット例を除去すると
全体の精度が84.7\%から77.3\%に低下しました（$-$7.4\,pp,
$p<0.001$; 表~\ref{tab:ablation}）。
この低下は中程度の難易度以上で観察され（簡単なものでは低下なし）、
中程度では$-$9.2\,ppの低下が見られました（表~\ref{tab:ablation-detail}）。
LLMはSQL生成パターン（テーブル名、JOINの順序、列名の使用）を
インコンテキスト学習~\cite{brown2020fewshot}を通じて習得します；
少数ショット例がない場合、LLMはスキーマ情報のみからSQLを推測しなければなりません。

\subsection{スキーマリンク}

GPT-5.5は入力クエリに関連するテーブルをスコアリングし、ソートします
（ソートのみのアプローチ）。
テーブルは除外されず、SQL生成のためのコンテキスト優先順序のみが変更されます。

\subsection{SQL生成と$n$-best候補}

GPT-5.5は$n$-best = 3のSQL候補を生成します。
アブレーションスタディでは、$n$-best = 1に切り替えた場合、
統計的に有意な精度の差は見られませんでした（$-$0.6\,pp, $p=0.069$）が、
平均レイテンシは31.0\,sから10.9\,sに減少しました
（表~\ref{tab:ablation}）。
\subsection{シュタイナー木JOIN制約}
\label{sec:schema_graph}

31のテーブル間のFK関係は、NetworkX~\cite{networkx2008}を使用して無向グラフとして表現されます。
FK関係は、PostgreSQLメタデータのイントロスペクションを介してランタイムで自動的に取得されます。
クエリに必要なテーブルのセットに対して、最小JOIN部分木はシュタイナー木近似を介して決定されます（アルゴリズム~\ref{alg:steiner}に示す通り）。

\begin{algorithm}[htbp]
  \caption{最小被覆JOIN部分グラフ（シュタイナー木近似）。}
  \label{alg:steiner}
  \begin{algorithmic}[1]
    \Require FK関係グラフ $G = (V, E)$, 必要なテーブルセット $R$
    \Ensure JOINパスリスト $P$
    \State $P \gets \emptyset$; ユニオンファインド $U$ を初期化
    \ForAll{$(s, t) \in \binom{R}{2}$}
      \If{$\text{Find}(s) = \text{Find}(t)$}
        \State \textbf{continue}
      \EndIf
      \State $p \gets \text{ShortestPath}(G, s, t)$ \Comment{FKグラフ上のBFS}
      \If{$p \neq \emptyset$}
        \State $P \gets P \cup \{p\}$
        \ForAll{隣接ノードペア $(u, v) \in p$}
          \State $\text{Union}(u, v)$
        \EndFor
      \EndIf
    \EndFor
    \State \Return $P$
  \end{algorithmic}
\end{algorithm}

ノード数 $|V| = n$ および必要なテーブル数 $|R| = k$ に対して、アルゴリズムは $O(k^2)$ のBFSトラバーサルを実行します。
31テーブル規模（$n = 31$, $k \leq 5$）では、これがミリ秒単位で完了します。

アブレーションスタディでは、シュタイナー木制約を削除した場合、統計的に有意な精度の差は示されませんでした（$+$0.0\,pp, $p=1.000$; 表~\ref{tab:ablation}）。
検証された範囲内では、現在の31テーブル規模では、ほとんどのクエリが5つのコアテーブル（\texttt{material\_entry}, \texttt{structure}, \texttt{element}, \texttt{composition}, \texttt{calculated\_property}）を使用して完了しており、観察可能な効果が制限されています。
テーブル数が増えるにつれて、その寄与が明らかになることが期待されます。

\subsubsection{PostgreSQLメタデータからのグラフ構築}

FK関係は、PostgreSQLの\texttt{information\_schema}からランタイムで動的に抽出されます：

\begin{lstlisting}[language=SQL,caption={FK関係の抽出},label=lst:fk_query,numbers=none]
SELECT tc.table_name, kcu.column_name,
       ccu.table_name, ccu.column_name
  FROM information_schema.table_constraints tc
  JOIN information_schema.key_column_usage kcu
    ON tc.constraint_name = kcu.constraint_name
  JOIN information_schema.constraint_column_usage ccu
    ON ccu.constraint_name = tc.constraint_name
 WHERE tc.constraint_type = 'FOREIGN KEY';
\end{lstlisting}

結果は、NetworkX~\cite{networkx2008}において無向グラフ $G = (V, E)$ として保存されます。
各エッジは、JOIN句生成時に使用される属性としてFKの方向を保持します。
FKメタデータはランタイムで読み取られるため、システムはスキーマの変更を追跡できます。

\subsubsection{複数要素ANDクエリ：EXISTSサブクエリ}
\label{sec:multi_element}

構成テーブルの正規化から生じる材料特有の課題は、「NiとAlの両方を含む化合物」のようなクエリです。
単純なアプローチ\texttt{WHERE c.element = 'Ni' AND c.element = 'Al'}は、どの行も両方の条件を満たさないため、常に0行を返します。
スキーマグラフエンジンは、複数の要素が指定されているときにそれを検出し、自動的にEXISTSサブクエリを生成します：

\begin{lstlisting}[language=SQL,caption={複数要素AND},label=lst:exists,numbers=none]
SELECT DISTINCT m.entry_id, m.formula
FROM material_entry m
WHERE EXISTS (SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Ni')
AND EXISTS (SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Al')
LIMIT 10000;
\end{lstlisting}

AND/ORの意図は、結合と助詞から条件抽出器によって分類されます。
OR指標には、\texttt{IN}句が使用されます。

\subsubsection{JOINパスからのSQL生成}

$P$内の各パスはSQL JOIN句に変換されます。
テーブルエイリアスは、すべての31テーブルに対して固定辞書から割り当てられます（\texttt{material\_entry}$\to$\texttt{m}, \texttt{composition}$\to$\texttt{c}など）。
同じテーブルが複数回出現する場合、数値サフィックスがユニークなエイリアスを生成します（\texttt{c2}, \texttt{c3}）。

\subsection{条件抽出器}
\label{sec:entity_extractor}

条件抽出器は、自然言語クエリを構造化された条件辞書に変換します。これは、YAMLベースのバイリンガル（日本語-英語）用語辞書（\texttt{material\_terms.yaml}）を使用します。

\subsubsection{辞書構造}

辞書は4つのカテゴリをカバーしています：
(1)~\textbf{プロトタイプエイリアス}（例：\texttt{L12} $\leftrightarrow$ [L1$_2$, Cu$_3$Au型, $\gamma'$]）、
(2)~\textbf{元素マッピング}（\texttt{Fe} $\leftrightarrow$ [鉄]）、
(3)~\textbf{安定性用語}（「安定」$\to$ \texttt{energy\_above\_hull} $\leq 0.001$~eV/atom; 「準安定」$\to$ $0.001 < E_\text{hull} \leq 0.05$）、
(4)~\textbf{特性用語}（「格子定数」$\to$ \texttt{structure.lattice\_a}など）。

Unicode下付き文字（U+2080--U+2089）は、マッチングの前にASCII数字に正規化されます。
元素記号の認識は、単語境界の正規表現を使用して「Fe」を「FeCoNi」の部分文字列から区別します。

\subsubsection{数値条件パーサ}

パーサは、5つのパターンを介して数値比較式を認識します（表~\ref{tab:numeric_patterns}）。
プロパティからカラムへのマッピングは、内部辞書（\texttt{\_PROPERTY\_COLUMN\_MAP}）によって管理されます。
浮動小数点比較の場合、「近い」や「比較可能」といった表現は、プロパティ固有の許容範囲を呼び出します（格子定数：$\pm 0.03$~\AA{}{}; $E_\text{hull}$：$\pm 0.001$~eV/atom）。

\subsubsection{化学式パーサと曖昧さ処理}

化学式トークンは3つのタイプに分類されます：
(1)~\textbf{exact\_formula}（\texttt{Ni3Al} $\to$ \texttt{formula = 'Ni3Al'}）、
(2)~\textbf{formula\_or\_reduced\_formula}（「NiAlのB2エントリ」$\to$ \texttt{reduced\_formula = 'AlNi'}）、
(3)~\textbf{contains\_elements}（「NiとAlを含む」$\to$ EXISTSサブクエリ）。
分類は文脈依存です：「含む」といった表現との共起は、\texttt{contains\_elements}処理を引き起こします。

\subsubsection{カバレッジスコア}
\label{sec:coverage_score}

カバレッジスコアは、辞書、元素辞書、または数値パターンによって認識されたクエリ内の意味トークンの割合を定量化し、$[0, 1]$の値を生成します。
このメトリックは、サイレント制約ドロップ（認識されない語彙の静的廃棄）を防ぎます。
スコアが$\geq 0.8$の場合、ルールベースモードの実行がトリガーされます；
$\geq 0.5$の場合はLLMモードにエスカレートします；
$< 0.5$の場合はユーザーからの確認を要求します。

\subsubsection{意図分類器}
\label{sec:intent_classifier}

ルールベースの意図分類器はSQL生成の上流に配置され、クエリを5つのカテゴリに分類します（db\_query / out\_of\_scope / ambiguous / unsafe / greeting）。
これは、20のVASP/DFTワークフローパターンの正規表現マッチカウントを9のDB特有パターンと比較し、範囲外の質問を事前にフィルタリングします。

材料科学の用語をSQL条件に直接マッピングする辞書を導入しました。
例えば、「$\gamma'$相」$\to$ \texttt{structure.prototype = 'L12'}、

\subsection{SQLGuard}
\label{sec:sqlguard}

sqlglot~\cite{sqlglot2023}を介したAST分析に基づき、
SQLGuardは生成されたSQLの安全性と一貫性を検証します。
検証は14のチェックから成ります：

\begin{enumerate}[nosep]
  \item カラム存在確認（ホワイトリスト照合）
  \item テーブル存在確認（許可されたテーブル照合）
  \item FK整合性のあるJOIN確認
  \item マルチステートメント検出（セミコロン分割）
  \item DMLキーワード検出（DROP/DELETE/INSERT/UPDATE）
  \item SQLインジェクションパターン検出
  \item LIMIT句の存在確認（欠如時は自動追加）
  \item DISTINCT推奨（JOIN時）
  \item SELECT * 禁止
  \item サブクエリのネスト深さ制限
  \item UNION/INTERSECT句の検証
  \item 算術演算の型の有効性
  \item ORDER BY/GROUP BYの参照整合性
  \item エイリアス解決後のカラム参照確認
\end{enumerate}

アブレーションスタディでは、SQLGuardを削除すると$-$0.2\,ppの低下が見られました
（$p=0.891$、統計的に有意ではない；表~\ref{tab:ablation}）。
無効なSQL候補に対して既に低いスコアを割り当てるため、SQLGuardが拒否するSQLが選択されることは
稀です。しかし、SQLGuardは精度の寄与とは独立した価値を持つセキュリティの安全網として機能します
（セクション~\ref{sec:injection_safety}を参照）。

\subsection{ハイブリッドリランカー}

SQL候補のリランキングにはGPT-5.5を使用します。
少数ショットの例選択にはクロスエンコーダー（ローカル、$<$50\,ms）を使用し、
SQL候補とスキーマのスコアリングにはGPT-5.5（API）を使用し、ハイブリッドアーキテクチャを形成します。

アブレーションスタディでは、リランカーを削除すると$-$3.3\,ppの低下が見られました
（$p=0.364$、統計的に有意ではない）。
Medium層では$-$6.7\,pp、Hard層では$-$5.6\,ppの低下が観察されました（表~\ref{tab:ablation}）。

90のクエリに対する別のA/B評価では、リランカーありで77.2\%、なしで69.4\%（$+$7.7\,ppの差）が示されました。
しかし、このA/B評価はアブレーションスタディとは異なる実行で行われており、直接比較には注意が必要です。

\subsubsection{日本語クロスエンコーダーの比較}

少数ショットの例選択に使用されるクロスエンコーダーについて、英語モデル（ms-marco-MiniLM-L-6-v2）と
日本語モデル（hotchpotch/japanese-reranker-cross-encoder-xsmall-v1）を20のVery Hardクエリで比較しました。
英語モデルは32.4\%を達成し、日本語モデルは28.1\%でした（$-$4.4\,ppの差がms-marcoに有利）。
少数ショットの例にはSQLコード（英語）が含まれているため、ms-marcoの英語スコアリング能力が
その優位性に寄与している可能性があります。

\subsection{修復ループ}
\label{sec:repair}

SQL実行エラーや結果の有効性の問題が検出された場合、エラーメッセージがLLM（GPT-5.5）にフィードバックされ、
最大3回の修復試行が行われます。
\section{データベースと評価設計}
\label{sec:evaluation}
\subsection{検証データベース}

提案された方法を検証するために、L1$_2$型金属間化合物に焦点を当てたデータベースを代表的な無機材料RDBとして使用しました。検証データベースはL1$_2$プロトタイプスキーマを中心に構成されており、31の正規化されたテーブルと1つのビュー（図~\ref{fig:er}）から成り、\texttt{material\_entry}が中心的なエンティティとして、組成、構造、安定性、計算された特性、電子構造、機械的特性、および表面特性のテーブルにFK関係を介して接続されています。この構造は、OQMD、Materials Project、AFLOWなどの無機材料データベースに共通する正規化スキーマを代表しています。主要な統計は表~\ref{tab:db_stats}に示されています。
\subsubsection{ソースOQMDスタイルデータレイアウトとの関係}

公開されているOQMDデータモデルは、少数の広いエントリ中心のテーブル（例：\texttt{entries}、\texttt{element\_ratios}、\texttt{formation\_energies}、\texttt{reference\_states}、および\texttt{elements}）で表現できます。このレイアウトは高スループットデータの蓄積に効率的ですが、構造的に異なる情報（組成、結晶構造、熱的安定性、電子特性）を、\texttt{delta\_e}や\texttt{composition\_formula}のような一般的なカラムに格納しています。自然言語インターフェースにおいて、これは曖昧さを引き起こします：「エネルギー」は生成エネルギー、ハル距離、またはバンドギャップを指す可能性があります。「Ti」は構成元素または特性フィルターのターゲットである可能性があります。

多段階CTE生成エンタルピー計算に使用される純元素の参照エネルギーはOQMDから取得され、化合物の格子定数、生成エネルギー、その他の特性は、\path{ingestion/generate_extended_data.py}によって生成された合成検証データです。これらの合成データは、材料科学の概念によってグループ化された31の正規化テーブルに割り当てられ（表~\ref{tab:schema_comparison}）、実際の無機材料RDBの構造を模倣しています。この正規化はタスクを簡素化するものではありません：評価用のSQLは平均して3.4テーブルを使用し、非常に難しいクエリでは最大6テーブル（および多段階CTE）を必要とします。むしろ、明示的なスキーマは各テーブルおよびカラムの物理的意味を明確にし、結合の複雑さの負担をユーザーからText-to-SQLパイプラインに移します。SteinerツリーJOINジェネレーター、スキーマリンク、および少数ショットの例は、この複雑さを処理するために正確に設計されています。

\subsection{評価クエリ}

私たちは100の著者設計のクエリを使用しました（表~\ref{tab:query_design}）。
各クエリには、ゴールドSQL、期待される実行結果（JSON）、必要なテーブル、およびJOINパスが注釈されています。
無機材料RDB用の標準的なText-to-SQLベンチマークは現在存在しないため、データベーススキーマ構造と材料研究者の典型的な情報ニーズに基づいて評価クエリを構築しました。
クエリは以下の原則に従って設計されました：
(1) 実際の材料研究で生じる質問をシミュレートする（例：安定相の検索、組成と特性の相関）、
(2) 難易度はゴールドSQLから計算された統一的な複雑性スコアによって4つの層に分類されます（必要なテーブルごとに$3$ + WHERE/HAVING条件ごとに$1$ + GROUP BYごとに$2$ + EXISTSサブクエリごとに$3$ + 派生サブクエリごとに$3$；易しい $<8$、中程度 $8$--$11$、難しい $12$--$16$、非常に難しい $\geq 17$）、
(3) すべてのカテゴリ（A--H）にわたってバランスの取れたカバレッジ、
(4) 高度な分析パターンを評価するために5つのCTEマルチステップ計算クエリが含まれています。
著者設計のクエリの制限として、クエリの分布が実際のユーザー使用パターンと異なる可能性があります；ユーザー研究は今後の検証タスクとして残ります。

\subsection{評価指標}

行レベルの再現率が主要な指標として使用されます。
生成されたSQLとゴールドSQLの実行結果は共通の列に投影され、行レベルの一致率が計算されます：
\begin{equation}
  \text{accuracy}(q) = \frac{|R_\text{gen}^{C} \cap R_\text{gold}^{C}|}{|R_\text{gold}^{C}|}
  \label{eq:column_aware}
\end{equation}
ここで、$C = \text{cols}(R_\text{gen}) \cap \text{cols}(R_\text{gold})$は共通の列セットであり、$R^C$は列セット$C$への投影を示します。
この指標は再現率ベースです：生成されたSQLがゴールドよりも多くの行を返す場合、ペナルティは発生しません。
評価中は、LIMIT 10{,}000がゴールドSQLと生成されたSQLの両方に均等に適用されます。

\subsection{探索結果の解釈に関する注意事項}

このセクションの化合物属性は合成検証データであるため、ランク付けされたランキングやスクリーニングされたセットは、実際の材料の設計仮説として解釈されるべきではありません。これらのクエリの目的は、提案された自然言語インターフェースが複雑な正規化スキーマに対して正しく多基準フィルタリング、ランキング、および抽出を実行できることを確認することです。明らかな傾向（例えば、高い体積弾性率や高い安定性）は合成生成手順の副産物であり、検証セットの代わりに実際のデータベースが置き換えられた場合にユーザーが実行できる探索の種類を示すためにのみ提示されています。

\subsection{無機材料RDBにおけるスキーマの障壁と自然言語アクセスの重要性}

我々の結果は、無機材料RDBにおけるデータ利用の主な障壁がスキーマ構造の理解にあることを再確認します。31のテーブルからなる正規化されたスキーマに対して、スキーマ、辞書、再ランカーを保持しつつも少数ショット例を用いないモデル（no\_fewshot条件）は、77.3\%の精度しか達成できず、スキーマ、少数ショット例、再ランカーを保持しつつも辞書を用いないモデル（no\_dict条件）は、ほぼ同等の77.4\%を示します（表~\ref{tab:ablation}）。非常に難しい層では、少数ショット例なしで48.3\%、辞書なしで37.1\%に低下し、いずれかの省略がドメイン特有の用語の取り扱いを著しく損なうことを示しています。これは、少数ショット例またはドメイン辞書のいずれかが欠如している場合、スキーマを意識したシステムが材料研究者の意図をSQLに正確に翻訳できないことを示しています。両方とも必要です。

自然言語インターフェースは、このスキーマの障壁を効果的に低減できます。少数ショット例と材料ドメイン辞書の併用により、精度は84.7\%に回復し、特にドメイン特有の語彙を多く使用する複雑なクエリで顕著な向上が見られます。この改善は、無機材料RDBへの自然言語アクセスが単なる利便性を超え、スキーマの障壁により以前はアクセスできなかったデータへの実質的なアクセスを可能にすることを示唆しています。具体的には、100\%の構文の有効性と100\%の実行成功を達成すること（表~\ref{tab:multiaxis}）は、SQLに不慣れな材料研究者が自然言語を通じて安全にデータベースを使用できることを意味します。93.2\%のJOINマッチ率は、正規化されたマルチテーブルRDBにおいてテーブル結合パスが高精度で特定されていることを示し、スキーマ理解の負担を大幅に軽減します。

スキーマの進化とデータの成長に関して、我々のパイプラインはFKメタデータベースの設計を採用しているため、テーブルの追加やFKの変更は自己反映されます。辞書と少数ショット例の更新には手動の努力が必要ですが、標準手順に減らすことができ（テーブル定義 $\to$ FK設定 $\to$ 辞書登録 $\to$ 少数ショット例追加）、運用維持コストを抑えることができます。

\subsection{少数ショット例の貢献}

少数ショット例を削除すると、すべてのコンポーネントの中で最大の精度低下が見られました（$-$7.4\,pp, $p<0.001$; 表~\ref{tab:ablation}）。この低下は、中程度の層以上で観察され、非常に難しい層では$-$10.3\,ppの低下が見られました（表~\ref{tab:ablation-detail}）。次いで、難しい層で$-$8.5\,pp、中程度の層で$-$9.2\,ppの低下があり、より複雑なクエリが少数ショット例に対してより大きな依存を持つことを示しています。少数ショット例なしでは、レイテンシも31.0\,sから50.7\,sに増加しました（表~\ref{tab:latency}）。これは、LLMが試行錯誤を通じてSQLを生成するためと考えられます。

\subsection{材料ドメイン辞書の貢献}

辞書を削除すると、全体で$-$7.3\,ppの低下が見られました（$p<0.001$）。ただし、効果は難易度層によって異なりました（表~\ref{tab:ablation-detail}）。簡単な層では低下は見られませんでしたが、難しい層では$-$9.3\,pp、非常に難しい層では$-$21.5\,ppの低下が見られました。

簡単および中程度のクエリは一般的な表現で構成されており、LLMは自らSQL条件を推測できます。対照的に、非常に難しいクエリは同時に複数のドメイン特有の用語を含み、辞書がないとLLMは正しいSQL条件を生成できない可能性があります（例：``$\gamma'$相'' $\to$ \texttt{structure.prototype = 'L12'}）。

\subsection{再ランカーの貢献}
\label{sec:reranker_discussion}

再ランカーを削除すると、$-$3.3\,ppの低下が見られました（$p=0.364$、統計的に有意ではありません）。この効果は、中程度（$-$6.7\,pp）および難しい層（$-$5.6\,pp）で観察されました（表~\ref{tab:ablation-detail}）。

しかし、非常に難しい層では、再ランカーを削除した際に$+$3.1\,ppの精度向上が見られました。この差は標準偏差の範囲内（VH層SD = 2.2\,pp）ですが、再ランカーは非常に難しい層では実際には逆効果を持つ可能性があります。この層では、すべての候補が部分的に不正確であることが多く、再ランカーは「より正しく見えるが実際には間違っている」候補を選択する可能性があります。特にCTEクエリでは、構文的には有効だが意味的には不正確な候補が高い再ランカーのスコアを得ることがあります。対照的に、中程度および難しい層では、少なくとも1つの正確な候補が存在することが多く、再ランカーはそれを正しく選択できます。これらの結果は、再ランカーの効果がクエリの複雑さに依存しており、高複雑度クエリに対する再ランク戦略の改善の余地があることを示唆しています。

\subsection{SQLGuard、$n$-best、およびシュタイナー木の貢献}

SQLGuard（$-$0.2\,pp、n.s.）、$n$-best（$-$0.6\,pp、n.s.）、およびシュタイナー木（$+$0.0\,pp、n.s.）はすべて統計的に有意ではない効果を示しました。

SQLGuardについては、再ランカーがすでに同等のフィルタリング機能を果たしているため、追加の効果を観察することが難しいです。その価値はセキュリティの安全網として独立して存在します。

$n$-best = 1に設定すると、精度を維持しつつレイテンシを31.0\,sから10.9\,sに短縮できます（表~\ref{tab:latency}）。これはコスト効率が優先される場合に有効な選択肢となります。

シュタイナー木については、現在の31テーブルの規模では、ほとんどのクエリが5つのコアテーブルのみを使用して完了し、その観察可能な精度効果が制限されています。しかし、JOINの幻覚の数を半減させる（シュタイナー木なしで6、ありで3；表~\ref{tab:error_analysis}）ことを示しており、その主な役割は生の精度ではなくJOINパスの健全性です。FK自己反映に基づくアーキテクチャを考慮すると、テーブルの数が増加する（例：OQMD統合後）か、他の正規化されたRDB（Materials Project~\cite{jain2013mp}、AFLOW~\cite{curtarolo2012aflow}）に適用されると、その利点が明らかになることが期待されます。

\subsection{アブレーション条件の定量的比較}

アブレーション条件は、1つのコンポーネントを除いた簡略化された手法として見ることができます（表~\ref{tab:ablation}）。no\_fewshot条件は、辞書と再ランカーを保持しながら少数ショットの例のみを除去し、77.3\% ($-$7.4\,pp)の精度を得ます。また、no\_dict条件は辞書のみを除去し、77.4\% ($-$7.3\,pp)の精度を得ます。これらは2つの最大の単一コンポーネントの低下であり、ほぼ同一であることから、少数ショットの例と辞書が全体の精度に対する2つの主要な寄与者であることを示しています。提案された完全な手法は84.7\%に達します。

アブレーションは1つのコンポーネントを一度に除去するため、明らかな段階的値は真の増分追加実験ではありません。コンポーネント間の相互作用により、寄与は厳密に加算的ではありません。同じデータベース上で他の手法（DIN-SQL、DAIL-SQLなど）との直接比較は行われていません（制限事項~6を参照）。LLMのみおよびスキーマのみ（少数ショットの例なし）構成の質的SQL例は、補足セクション~\ref{sec:sup_sql_examples}に提供されています。

\subsection{多段階計算クエリの処理}
\label{sec:multistep_query}

無機材料RDBへの自然言語アクセスにおける重要な要件は、派生量計算を伴う多段階データ抽出です。代表的なケースとして、クエリ``Ni$_3$Alの生成エンタルピーを純元素参照を用いて計算せよ''を考えます。このクエリに正しく答えるためには、以下の多段階データ抽出と計算が必要です：
\begin{enumerate}
  \item \texttt{phase\_stability}テーブルから化合物Ni$_3$Alの生成エネルギー$E_\mathrm{f}$を取得する。
  \item \texttt{composition}テーブルから構成元素NiとAlの組成比$x_i$を取得する。
  \item \texttt{pure\_element\_reference}テーブルから各元素の基底状態エネルギー$E_\mathrm{ref}(i)$を取得する（OQMD由来、89元素）。
  \item 加重参照エネルギー$\sum_i x_i E_\mathrm{ref}(i)$を計算する。
  \item 修正された生成エンタルピー$\Delta H_\mathrm{f} = E_\mathrm{f} - \sum_i x_i E_\mathrm{ref}(i)$を出力する。
\end{enumerate}

この操作は単一テーブルのルックアップではなく、3テーブルのJOIN、サブクエリによる集計計算、および算術演算を含むCTE（共通テーブル式）としてSQLに変換する必要があります。我々のパイプラインは、LLMが\texttt{formation\_enthalpy}ビューを介して単純なクエリを生成し、対応する少数ショットの例を追加することで明示的なCTEベースの計算を行うことを可能にします。

従来のテキストからSQLへのベンチマーク（Spider~\cite{yu2018spider}、BIRD~\cite{li2024bird}など）は、主にSELECT--WHERE--JOIN--GROUP BYの組み合わせをカバーしており、科学計算に不可欠な多段階データ統合および派生量計算を必要とするクエリは含まれていません。材料データベースにおいて、生成エンタルピー、体積サイズ因子、格子不整合などの派生量は研究上重要であり、そのような計算を自然言語で直接指示できる能力は、材料情報学における自然言語インターフェースの実用性を大幅に向上させます。
\subsection{独立に設計されたクエリによる評価}
\label{sec:independent_eval}

自己参照バイアスを検証するために、パイプラインの実装には関与していない共同著者の末松千恵によって独立に設計された100のクエリを使用して精度を再評価しました。これらのクエリは、クエリ設計と独立評価に貢献しました（簡単18 / 中程度34 / 難しい34 / 非常に難しい14）、10のカテゴリ（基本検索、構成/要素、構造/格子定数、安定性/形成エネルギー、DFT計算/特性、電子構造/磁気/熱特性、表面/粒界/欠陥、文献/合成/応用、材料設計/スクリーニング、比較/統計）にわたっています。これらのクエリは、アブレーション研究で使用されたのと同じ連続実行リコールメトリックと難易度分類でスコアリングされました。

全体の実行精度は76.9\%（簡単94.4\% / 中程度81.7\% / 難しい61.5\% / 非常に難しい80.4\%）で、著者設計のセット（84.7\%; 表~\ref{tab:ablation}）よりも7.8\,pp低いです。このギャップは主に3つの要因に起因しています：

\textbf{(1) テーブルカバレッジバイアス}（主な要因）：
著者設計のゴールドSQLはコアテーブルのセットを使用していますが、独立に設計されたクエリは、\texttt{elastic\_tensor}、\texttt{magnetic\_property}、および\texttt{surface\_energy}などの追加テーブルを参照しており、少数ショットの例がまばらです。

\textbf{(2) 少数ショット最適化バイアス}：
ほとんどの著者設計のクエリは、固定パターンとして「L1$_2$」を明示的に含んでおり、少数ショットの例はこのパターンに最適化されています。独立に設計されたクエリは、より多様な表現を使用しています。

\textbf{(3) 語彙の多様性}：
独立に設計されたクエリは、現在のパイプラインが明示的なキーワードマッチングに依存しているため、難しい暗黙の条件指定を頻繁に使用します。

構文の有効性（100.0\%）は両方のセットで一貫しており、スキーマグラフ制約のクエリ起源の独立性を確認しています。非常に難しい層（80.4\%）は難しい層（61.5\%）よりも高いのは、14の非常に難しいクエリが少数ショットの例でカバーされているいくつかの短いCTEパターンを含んでいるのに対し、いくつかの難しいクエリは少数ショットのサポートなしに周辺テーブルを参照しているためです。詳細な結果は補足資料~\ref{sec:sup_expert_queries}に提供されています。

\subsection{列間比較クエリの取り扱い}
\label{sec:column_comparison}

多段階計算に加えて、列間比較は材料研究で頻繁に遭遇する重要なクエリパターンです。「値Aが値Bより小さいエントリを見つける」という形式のクエリは、同じ行内の異なる列の値を比較する条件式を用いたSQL生成を必要とするため、単一の閾値フィルタリング（\texttt{WHERE col > 0.5}）とは異なります（\texttt{WHERE col\_a > col\_b}）。

私たちのパイプラインは、3種類の列間比較パターンをカバーする少数ショットの例を提供します：
\begin{enumerate}
  \item \textbf{テーブル内比較}：
    同じテーブル内の2つの列の直接比較。
    例：\texttt{formation\_energy\_per\_atom < energy\_above\_hull}（\texttt{phase\_stability}テーブル内）；
    \texttt{bulk\_modulus\_vrh > 2.0 * shear\_modulus\_vrh}（\texttt{elastic\_tensor}テーブル内、Pugh延性メトリック）。
  \item \textbf{テーブル間比較}：
    JOINを介して異なるテーブルの列を比較。
    例：\texttt{thermal\_property.debye\_temperature\_k > magnetic\_property.curie\_temperature\_k}；
    総磁化対絶対形成エネルギー。
  \item \textbf{集約関数を用いた比較}：
    GROUP BY--HAVINGと組み合わせて、構成要素間の電気陰性度差などの導出量に対する閾値評価を行います。
    例：\texttt{HAVING MAX(electronegativity) - MIN(electronegativity) > 0.5}。
\end{enumerate}

これらのパターンは、定数比較（\texttt{WHERE col > 0.5}）に比べてLLMが正しく生成するのが難しいです。特にテーブル間比較は、スキーマ情報から各比較列がどのテーブルに属するかを正確に特定する必要があります。私たちは、主に列間比較パターンを追加して少数ショットの例プールを45例に拡張し、LLMがそのようなパターンを学習できるようにしました。

\subsection{RDBスキーマ設計とText-to-SQLコスト}
\label{sec:schema_design_cost}

この研究を通じて得られた重要な洞察は、RDB自体のテーブル構造がText-to-SQL精度を決定する上流要因であるということです。

高度に正規化されたスキーマでは、単一のクエリに対して複数のテーブルJOINが必要であり、LLMが生成しなければならないSQLの複雑さが増します。私たちのデータベースにおける形成エンタルピー計算（セクション~\ref{sec:multistep_query}）では、\texttt{phase\_stability}、\texttt{composition}、および\texttt{pure\_element\_reference}の3テーブルJOINが必要であり、さらにCTEベースの集約計算が必要でした。少数ショットの例なしでの精度の$-$7.4\,ppの低下は、より複雑なテーブル間結合パターンがLLMによる正確なSQL生成をより困難にすることを確認しています。

この洞察に基づいて、T2SQL準備のための以下のスキーマ設計戦略を考慮できます：
\begin{enumerate}
  \item \textbf{ビューによる複雑さの隠蔽}：
    よく使用される多段階JOINパターンをビューまたはマテリアライズドビューとして定義し、LLMに対して単一のSELECTでクエリ可能なインターフェースを提供します。この研究における\texttt{formation\_enthalpy}ビューがその例です。
  \item \textbf{クエリ頻度に基づく非正規化}：
    よく参照されるテーブルグループ（例：\texttt{composition}と\texttt{element}）を事前に結合されたテーブルとして提供し、JOINの数を減らします。
  \item \textbf{自己記述的な列名付け}：
    列名にテーブルのコンテキストを埋め込み（例：\texttt{energy} $\to$ \texttt{formation\_energy\_per\_atom}）、LLMがスキーマ情報から適切な列を選択する確率を高めます。
  \item \textbf{明示的なFK制約定義}：
    スタインナー木アルゴリズムはFK関係に基づいて最小JOINパスを決定します。自動JOIN解決はFK制約が欠如しているスキーマでは失敗します。T2SQL準備が設計目標である場合、包括的なFK制約の定義が必要です。
\end{enumerate}

要約すると、Text-to-SQLシステムの精度を向上させるには、パイプライン側の改善だけでなく、データベーススキーマ設計段階でのNLインターフェースの互換性を考慮する必要があります。この視点は、この研究で使用された検証DBだけでなく、類似の正規化スキーマを持つ無機材料RDB（OQMD、Materials Project、AFLOWなど）や、Text-to-SQLが適用されるドメイン特化型RDBに一般的に適用可能な設計ガイドラインとして機能します。
\subsection{CTEマルチステップ計算クエリの評価}
\label{sec:cte_evaluation}

CTE（共通テーブル式）を用いたマルチステップ計算クエリの能力を定量的に評価するために、形成エンタルピー計算を例として、5つの非常に難しいクエリをCTEクエリに置き換え、評価を実施しました。これらの5つのクエリは以下のカテゴリをカバーしています。

\begin{enumerate}[nosep]
  \item \textbf{シンプルCTE}（導出量計算）:
    特定の化合物の$\Delta H_f$を純元素参照を用いて計算する
  \item \textbf{CTE + フィルター}:
    安定したL1$_2$化合物の$\Delta H_f$を計算し、閾値でフィルタリングする
  \item \textbf{CTE + 集約}:
    Aサイト元素ごとの平均$\Delta H_f$を集約する
  \item \textbf{マルチステージCTE}（2段階以上）:
    3段階CTE: 安定性フィルター $\to$ $\Delta H_f$計算 $\to$ 元素フィルター
  \item \textbf{CTE + クロスカラム比較}:
    形成エネルギーと加重純元素参照の差を通じた安定性評価

CTEサポートの適用限界を定量化するために、10の新しいパターン（ウィンドウ関数、HAVINGフィルター、2段階集約、弾性/熱/磁気テーブルへのJOIN、条件付き集約、3段階CTEなど）を追加し、合計15のクエリを評価しました。少数ショット例でカバーされた5つの元のパターンは100\%を維持しましたが、10の新しいゼロショットパターンはわずか42.3\%に達し、全体で61.6\%となりました。この結果は、アブレーションで観察された少数ショットの重要な寄与（$-$7.4\,pp, $p<0.001$）と一致しており、マルチステップ計算サポートの範囲は少数ショット例のパターンカバレッジによって制御されていることを示しています。したがって、新しいマルチステップパターンへの拡張は、ドメイン専門家によって追加された少数の例（パターンごとに約1つ）を通じて達成可能であり、モデルの再トレーニングなしに実現できるというこの設計の実用的な利点です。

\subsection{類似無機材料RDBへの拡張性}
\label{sec:extensibility}

本研究で得られた設計原則は、検証に使用された特定のデータベースに限定されません。FKイントロスペクションに基づくシュタイナー木アルゴリズムは、テーブルの追加やスキーマの変更を必要とせず、定義されたFK制約を持つ任意の正規化されたRDBで動作します。ドメイン辞書については、新しい材料システム（ヘウスラー、ペロブスカイトなど）や異なるデータベースに適用する際に語彙の追加が必要ですが、辞書の構造自体（4つのカテゴリ：プロトタイプエイリアス、元素マッピング、安定性用語、特性用語）は一般的に無機材料RDBに適用可能です。

しかし、以下の注意点に留意する必要があります。本研究の主な評価は単一のOQMD由来のデータベースに基づいています；セクション~\ref{sec:transfer_eval}ではスキーマの名前変更、難読化、プロトタイプの拡張、実際のMaterials Project風スキーマへの一般化が示されましたが、根本的に異なる意味論を持つRDBや、はるかに大規模なRDBへの一般化性能を主張するものではありません。少数ショットの例は検証DBスキーマに依存しており、異なるRDBに適用する際にはドメイン専門家による新しい例の設計が不可欠です。これらの制限を考慮に入れた上で、本研究は無機材料RDBへのNLアクセスのための設計原則の一つのデモンストレーションを提供します。

\subsection{制限事項と今後の研究}

\begin{enumerate}
  \item \textbf{単一データベースの検証}:
    本研究の主な評価はOQMD由来のL1$_2$データベース（31テーブル、1{,}559エントリ）に基づいています。ゼロ適応転送テスト（セクション~\ref{sec:transfer_eval}）では、スキーマの名前変更（90.5\%）、難読化された識別子（90.0\%）、プロトタイプの拡張（90.0\%）、および実際のMaterials Project風スキーマ（100.0\%）への一般化が示されましたが、根本的に異なる意味論やスケールを持つRDBへの一般化は確認されていません。
  \item \textbf{統計テストの範囲}:
    ウィルコクソン符号付き順位検定が、5回の実行にわたって完全条件に対するクエリごとの精度差（$n=100$）に対して実施されました。実行回数は限られており、複数比較の補正は適用されていません；ブートストラップや他の方法は、より正確な信頼区間のために有用です。
  \item \textbf{クエリのカバレッジ}:
    100の著者設計のクエリは、材料研究における主要な検索パターンをカバーするように設計されていますが、実際の使用で遭遇する多様なクエリパターンを網羅的にカバーしているわけではありません。
  \item \textbf{ゴールドSQLの検証}:
    ゴールドSQLと期待される結果は著者によって作成されました；独立に設計された100クエリセットは、共同著者の末松千恵によってクロスチェックされましたが、外部研究者による完全な独立第三者検証は行われていません。
  \item \textbf{辞書のカバレッジ}:
    492用語の辞書はL1$_2$探索に特化しています；ヘウスラー、ペロブスカイト、その他のシステムへの拡張には手動登録が必要です。スキーマメタデータからの半自動生成への移行が望まれます。
  \item \textbf{ベースラインの公平性}:
    同じデータベースに対する他の手法（DIN-SQL、DAIL-SQLなど）との直接比較は行われていません。
\end{enumerate}

\subsection{今後の展望}

\begin{enumerate}
  \item \textbf{他の無機材料RDBでの検証}:
    Materials ProjectやAFLOWなど、異なるスキーマを持つ無機材料RDBへの適用を通じて設計原則の一般性を検証します。
  \item \textbf{大規模データの検証}:
    OQMDの単一元素データを統合することで、10{,}000エントリ規模でのシュタイナー木探索とSQL生成の精度を検証します。
  \item \textbf{拡張CTE評価}:
    本研究では5つのCTEクエリで100\%の精度が確認されました（セクション~\ref{sec:cte_evaluation}）；より多様な導出量パターン（相安定性図、弾性異方性メトリクスなど）への評価を拡張します。
  \item \textbf{AI4Sエージェントの統合}:
    MCPプロトコルまたは関数呼び出しを介して、自律材料探索エージェントのツールとしてT2SQLメソッドを組み込みます。
  \item \textbf{CALPHADの統合}:
    スキーマグラフのトラバーサルによってRDBから候補を絞り込み、その後温度依存の相安定性評価のためにCALPHAD自由エネルギー計算を行う二段階のフロー。
  \item \textbf{多軸評価指標}:
    SELECT列の精度、JOINパスの一致率、Top-$k$精度などを別々に評価し、エラーの原因特定を促進します。
\end{enumerate}
\section{結論}

\label{sec:conclusion}

本研究は、無機材料RDBへの自然言語アクセスを可能にする設計原則を提示し、L1$_2$相間化合物RDBを検証対象としてその有効性を示します。

7つの条件 $\times$ 100のクエリ $\times$ 5回の実行（合計3{,}500回の評価）におけるアブレーションスタディでは、材料ドメイン辞書（$-$7.3\,pp, $p<0.001$）と少数ショット例（$-$7.4\,pp, $p<0.001$）が材料特有のクエリパターンに不可欠であることが示されました。特に、多元素条件、化合物特性検索、ドメイン特有の用語を含むクエリにおいて顕著な改善が観察されました。エラー分析により、残る主要な失敗モードはJOINパスエラーではなくWHERE句条件の組み合わせエラーであることが明らかになりました（セクション~\ref{sec:error_analysis}）。

合成検証データを使用して、インターフェースはエントリを複合スコアでランク付けし、162の安定/準安定組成を抽出しました（セクション~\ref{sec:materials_evaluation}）。これらの結果は、実際の材料設計予測ではなく、複雑なスキーマにおける検索機能を示しています。100の独立に設計されたクエリによる外部検証では76.9\%の精度が達成されました。著者が設計したクエリとの精度差（約8\,pp）は、主にテーブルカバレッジバイアスと少数ショット最適化バイアスに起因しています（セクション~\ref{sec:independent_eval}）。

CTE（共通テーブル式）による多段階計算クエリ（生成エンタルピー計算など）において、少数ショット例でカバーされた5つのパターンは、完全条件下で100\%を達成しました（少数ショット例なしでは76\%、辞書なしでは86\%に低下）。さらに、10の新しいパターンを追加した15クエリの拡張評価では、ゼロショットの新しいパターンが42.3\%のままであることが示され、少数ショットパターンのカバレッジが多段階計算サポートの範囲を支配していることが示されました（セクション~\ref{sec:cte_evaluation}）。さらに、すべてのテーブルおよびカラム名が変更された未見のスキーマに対するゼロ適応転送テストでは90.5\%（非常に難しい100\%）を達成し、設計のスキーマ非依存性を示しました（セクション~\ref{sec:transfer_eval}）。

本研究を通じて得られたもう一つの重要な知見は、RDBスキーマの正規化の程度とテーブル構造がText-to-SQL精度の上流要因であるということです（セクション~\ref{sec:schema_design_cost}）。ビュー定義による複雑さの隠蔽、自己記述的なカラム名付け、包括的なFK制約定義などのスキーマ設計戦略は、パイプライン側の強化と並行して精度向上に寄与する可能性があります。この視点は、本研究で使用された検証DBだけでなく、同様の正規化スキーマを持つ無機材料RDB全般に適用可能な設計ガイドラインとして機能します。

FKイントロスペクションに基づくシュタイナー木アーキテクチャは、スキーマの変更を自動的に追跡でき、辞書や少数ショット例の更新により、Materials Integration (MInt)システム~\cite{minamoto2020mint}や系譜管理システムpinax~\cite{minamoto2026pinax}などの他の材料RDBへの適用が期待されます。転送テストはスキーマの名前変更への一般化を示しましたが、実質的に異なる正規化構造やスケールを持つRDBへの一般化性能の確認は今後の課題です。すべての評価は5回の独立した実行からの平均 $\pm$ 標準偏差として報告され、統計的有意性はウィルコクソン符号付き順位検定によって確認されています。

\section{生成されたSQL例}
\section{生成されたSQLの例}
\label{sec:sup_sql_examples}

代表的なクエリに対する生成されたSQLの例を、3つのメソッド構成（LLMのみ、フルスキーマ、我々の方法）で比較します。これは、各構成における出力SQLの質的な違いを具体的に示すことで、表~\ref{tab:ablation}における定量的比較を補完します。

\subsection{``Niを含む安定なL1$_2$化合物のリスト''}

\paragraph{LLMのみ（スキーマなし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT formula, stability
FROM materials
WHERE element = 'Ni'
  AND structure_type = 'L12'
  AND stability = 'stable';
-- テーブルの幻影: materials, stability などは存在しない
-- 実行不可（ERROR: relation "materials" does not exist）
\end{lstlisting}

\paragraph{フルスキーマ（プロンプト内にスキーマ、少数ショット例なし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT m.formula, ps.is_stable
FROM material_entry m
  JOIN composition c ON c.entry_id = m.entry_id
  JOIN structure s ON s.entry_id = m.entry_id
  JOIN phase_stability ps ON ps.entry_id = m.entry_id
WHERE c.element = 'Ni'
  AND s.strukturbericht = 'L12'
  AND ps.is_stable = true;
-- 実行可能だが不完全:
-- (1) プロトタイプ条件なし（L12がstrukturberichtにない場合を見逃す）
-- (2) DISTINCT/LIMITなし
-- (3) lattice_aのような実質的に有用な列を選択しない
\end{lstlisting}

\paragraph{我々の方法（スキーマグラフ + 少数ショット + 辞書）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT DISTINCT m.entry_id, m.formula,
  s.prototype, s.lattice_a, s.space_group
FROM material_entry m
  JOIN composition c ON c.entry_id = m.entry_id
  JOIN structure s ON s.entry_id = m.entry_id
  JOIN phase_stability ps ON ps.entry_id = m.entry_id
WHERE (s.prototype = 'L12'
    OR s.strukturbericht = 'L12')
  AND c.element = 'Ni'
  AND ps.energy_above_hull <= 0.001
LIMIT 10000;
-- スキーマグラフのトラバースにより3つのJOINのみ必要
-- テーブルの幻影なし、DISTINCTとLIMITを含む
\end{lstlisting}

\subsection{``NiとAlの両方を含むL1$_2$化合物のリスト''}

\paragraph{LLMのみ（スキーマなし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT * FROM compounds
WHERE elements LIKE '%Ni%' AND elements LIKE '%Al%'
  AND crystal_structure = 'L12';
-- テーブルの幻影: compounds, elements列は存在しない
\end{lstlisting}

\paragraph{フルスキーマ（少数ショット例なし）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT m.entry_id, m.formula
FROM material_entry m
  JOIN composition c ON c.entry_id = m.entry_id
  JOIN structure s ON s.entry_id = m.entry_id
WHERE c.element = 'Ni' AND c.element = 'Al'
  AND s.prototype = 'L12';
-- 致命的: 単一の行が両方の条件を同時に満たすことはできない -> 常に0行
\end{lstlisting}

\paragraph{我々の方法（EXISTSサブクエリ）:}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,breaklines=true]
SELECT DISTINCT m.entry_id, m.formula
FROM material_entry m
  JOIN structure s ON s.entry_id = m.entry_id
WHERE (s.prototype = 'L12'
    OR s.strukturbericht = 'L12')
AND EXISTS (
  SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Ni')
AND EXISTS (
  SELECT 1 FROM composition
  WHERE entry_id = m.entry_id AND element = 'Al')
LIMIT 10000;
-- EXISTSサブクエリによる正確な多元素AND
\end{lstlisting}
