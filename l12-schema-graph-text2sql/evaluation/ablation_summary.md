# Ablation Study: コンポーネント寄与度分析

## 概要

無機材料データベースのためのグラフ制約付きText-to-SQLパイプラインにおける
7コンポーネントの寄与度をablation studyにより定量化した。

- **評価規模**: 7条件 x 100クエリ = 700評価
- **モデル**: GPT-5.5
- **データセット**: 著者版100件（Easy 20 / Medium 30 / Hard 30 / Very Hard 20）

## 2. コンポーネント寄与度ランキング

### 第1位: Few-shot例 (Delta = -12.5pp)

Few-shotの除去は全難易度で精度低下を引き起こす唯一のコンポーネント。

- **Easy帯**: 100% -> 95% (-5pp) -- 単純クエリでもfew-shot例がSQL構文のアンカーとして機能
- **Medium帯**: 96.1% -> 79.6% (-16.5pp) -- JOIN構造やWHERE条件の生成にfew-shot例が不可欠
- **Hard帯**: 80.4% -> 66.8% (-13.6pp) -- 複雑なサブクエリ・集約でfew-shot例が型を提供
- **Very Hard帯**: 38.5% -> 26.2% (-12.3pp) -- 多テーブルJOINでもfew-shot例の効果維持

**解釈**: LLMはfew-shot例からSQL生成のパターン（テーブル名、JOIN順序、カラム名の使い方）を
学習しており、これがなくなると「データベーススキーマだけから正しいSQLを推論する」必要が生じ、
大幅に精度が落ちる。特にMedium帯の-16.5ppが顕著で、中程度の複雑さのクエリほどfew-shot例への
依存度が高いことを示す。

### 第2位: 材料ドメイン辞書 (Delta = -6.7pp)

ドメイン辞書の効果はVery Hard帯で最も顕著（-22.7pp）。

- **Easy/Medium帯**: 変化なし -- 単純なクエリではLLMがドメイン用語を正しく処理可能
- **Hard帯**: 80.4% -> 73.1% (-7.3pp) -- L1_2、gamma'相等のSQL条件マッピングが失敗
- **Very Hard帯**: 38.5% -> 15.8% (-22.7pp) -- 複合条件で辞書ベースのマッピングが不可欠

**解釈**: 辞書は「gamma'相」->「structure.prototype = 'L12'」のような
ドメイン固有の用語-SQL条件変換を担っている。Easy/Mediumクエリは汎用的な表現
（「バルクモジュラスが高い」等）で済むが、VHクエリは複数のドメイン用語を
同時に含み、辞書なしではLLMがこれらを正しいSQL条件に変換できない。

### 第3位: ハイブリッドReranker (Delta = -4.1pp)

Rerankerの効果はMedium/Hard帯で顕著。

- **Easy帯**: 変化なし -- 候補1つでも正解
- **Medium帯**: 96.1% -> 89.5% (-6.6pp) -- 3候補からの最良選択で改善
- **Hard帯**: 80.4% -> 74.1% (-6.3pp) -- LLMスコアリングが正しい候補を選別
- **Very Hard帯**: 38.5% -> 37.4% (-1.1pp) -- 全候補が不正確な場合は効果限定

**構成**: Cross-Encoder (ms-marco-MiniLM, Few-shot選択) + GPT-5.5 (SQL候補/Schema)

**別途90件評価**: Reranker ON 77.2% vs OFF 69.4% (Delta = +7.7pp)

### 第4-6位: SQLGuard / n-best / Steiner木 (各 Delta = -0.2pp)

現在のデータ規模・モデル性能では効果が限定的。

**SQLGuard (-0.2pp)**:
Rerankerが先に不正SQL候補を低スコアにするため、SQLGuardが拒否すべきSQLが
既に選ばれていない。ただし安全網としての価値（不正SQL実行防止）は変わらない。

**n-best (-0.2pp)**:
n_best=3 vs n_best=1の差がほぼない。ただしレイテンシは33s -> 13sに半減。
コスト効率を重視する場合はn_best=1が有力な選択肢。

**Steiner木 (-0.2pp)**:
30テーブル中、大半のクエリが5コアテーブル（compound, structure, element,
composition, calculated_property）で完結するため、最小部分木探索の効果が限定的。
テーブル数が100+に拡大した場合に効果が顕在化すると予想される。

## 4. 日本語reranker比較（VH 20件）

| Cross-Encoder | VH Accuracy | Latency |
|---------------|-------------|---------|
| ms-marco-MiniLM (現行) | 32.4% | 64.2s |
| hotchpotch/japanese-xsmall | 28.1% | 65.9s |
| **差** | **-4.3pp** | +1.7s |

**結論**: 日本語rerankerは現行ms-marcoに劣る。
Few-shot例にSQLコード（英語）が含まれるため、英語に強いms-marcoが有利。
ms-marco維持が最適。
