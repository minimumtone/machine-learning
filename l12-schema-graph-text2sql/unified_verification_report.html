1.1 3つの処理レベルの定義

本レポートでは、Text-to-SQL（T2SQL）の処理を3段階に分けて比較する。 各レベルは前のレベルの機能を包含した上位互換の関係にある。

Level 0: Naive T2SQL

処理内容：自然言語から条件（元素名、prototype名等）だけを抽出し、 データベースの全テーブルを無条件にJOINしてWHERE句を付けるだけの最も単純な方式。

特徴：

  • Schema Graph（テーブル間関係の解析）を使わない
  • DISTINCT（重複除去）を付けない → JOINの増殖で同じ行が何十回も出る
  • LIMIT（件数制限）を付けない → 全件返却
  • SQL Guard（安全検査）がない → SQL injectionに脆弱
  • 複数元素のAND検索（「NiとAlを両方含む」）が構造的に不可能

結論：実用には不適。「何もしなかったらどうなるか」のベースライン。

Level 1: Schema Graph T2SQL（Rule-based）

処理内容：Level 0の条件抽出に加え、Schema Graph Traversal Engine（NetworkXグラフ）で テーブル間のFK（外部キー）関係を解析し、必要最小限のテーブルだけをJOINする。 LLM（大規模言語モデル）は使わず、辞書＋正規表現のパターンマッチングで動作する。

特徴：

  • Schema Graphが最短JOIN経路を自動探索 → 不要テーブルを排除
  • DISTINCT・LIMIT 100を自動付与
  • SQL Guard（sqlglot構文検証 + 禁止キーワード検出）で安全性を担保
  • APIキー不要 → 完全オフライン動作・コスト0・<100ms
  • 決定的出力（同じ入力 → 常に同じSQL）

制限：辞書（material_terms.yaml）に未登録の用語は認識できない。 数値条件（「band_gap > 1.0 eV」）のWHERE句を自動生成できない。

Level 2: Schema Graph + LLM（GPT-5）

処理内容：Level 1の全機能に加え、LLM（本検証ではOpenAI GPT-5）がSQL生成を担当する。 プロンプトにはXMLスキーマ情報・許可テーブル/カラム一覧・Few-Shot事例（過去の成功SQL）が注入される。

特徴：

  • 辞書に未登録の元素（Xe, Rn等）や表現も認識可能
  • 「NiAlのL12」のような略記から意図を正確に推定
  • 数値条件（「band_gap > 1.0 eV」）のWHERE句を生成可能
  • Few-Shot事例（RAG）により、過去の成功パターンを参考にして精度向上
  • Schema制約（許可テーブル/カラムのみをプロンプトで指定）でハルシネーションを抑制

制限：平均~7.3秒/件（Level 1の~70倍）。APIコスト発生。 非決定的出力。クエリ内容が外部APIに送信される。

2.2 取得フィールド

OQMD-APIから各エントリについて以下のフィールドを取得し、PostgreSQLに投入した：

  • entry_id: OQMD内の一意識別子
  • formula / reduced_formula / chemical_system: 化学式・還元式・構成元素系
  • prototype / strukturbericht: 結晶構造型
  • lattice_a: volume_per_atom から立方晶として逆算した格子定数 (a = (V×N)1/3)
  • formation_energy_per_atom: 原子あたり形成エネルギー (eV/atom)
  • energy_above_hull: 凸包からのエネルギー差。0 = 熱力学的安定相
  • band_gap: バンドギャップ (eV)
  • space_group: 空間群記号

2.3 スキーマ拡張

OQMDデータに合わせて以下のカラムを追加した：

  • phase_stability.band_gap (REAL): バンドギャップ
  • structure.space_group (TEXT): 空間群記号
  • material_terms.yaml: band_gap, volume_per_atom, space_group の日英対応を追加
注意：OQMDのAPIは格子定数(lattice_a, b, c)を直接返さない。 volume_per_atom フィールドから立方晶を仮定して a = (V × N_atoms)1/3 で逆算した値を使用している。 非立方晶の化合物（B2のうち正方晶に歪んだもの等）では誤差が生じる。

3. E-R図とXML/RAGによるスキーマ注入

3.1 E-R図（7テーブル構成）

材料データベースは以下の7テーブルで構成される。各テーブル間はFK（外部キー）で関連付けられている。 下図はテーブル間の関係を視覚化したE-R図である。

図の読み方：

  • 矢印（→）はFK（外部キー）関係を示す。矢印の元テーブルが参照元、先テーブルが参照先
  • 紺色: material_entry（中心テーブル。全テーブルの基点）
  • 青色: composition, structure, phase_stability（material_entryに直接FKで接続。1-hop JOIN）
  • 緑色: calculation, calculated_property（2-hop JOIN。material_entry → calculation → calculated_property）
  • 紫色: data_source（参照テーブル。破線は任意結合を示す）

Schema Graph Traversalの観点：「Feを含む安定なB2化合物」というクエリの場合、 必要なのは composition（Fe）+ structure（B2）+ phase_stability（安定性）の3テーブルだけ。 Schema Graphはこの3テーブルへの最短経路（全て material_entry 経由の1-hop）を自動的に発見し、 不要な calculation / calculated_property / data_source のJOINを排除する。

3.2 XMLによるスキーマ構造化

E-R図の情報をXML形式で構造化し、LLMプロンプトに注入する。 これにより、LLMはテーブル名・カラム名・FK関係を「知識」として持った状態でSQLを生成できる。

<schema> <table name="material_entry"> <column name="entry_id" type="TEXT" pk="true"/> <column name="formula" type="TEXT"/> </table> <table name="composition"> <column name="entry_id" type="TEXT" fk="material_entry.entry_id"/> <column name="element" type="TEXT"/> </table> <relationship from="composition.entry_id" to="material_entry.entry_id"/> </schema>

このXMLスキーマは RAG (Retrieval-Augmented Generation) の一形態として機能する。 従来のRAGはベクトルDBから関連文書を検索して注入するが、ここではスキーマ構造そのものを 「検索された知識」としてプロンプトに注入している。

3.3 Schema Graph Traversal Engineの重要性

XMLスキーマを NetworkX有向マルチグラフ に変換し、テーブル間のJOIN経路を自動探索する。

なぜ重要か：

  • Naive T2SQL（Level 0）の致命的問題： 全テーブルを無条件にJOINすると、不要なテーブルのJOINにより結果が増殖（CROSS JOIN的な振る舞い）、 または存在しないFK経路でJOINして0件になる。
  • Schema Graphの解決策： 条件抽出で特定されたカラムが属するテーブルだけを選び、 それらのテーブル間の最短FK経路をグラフ探索（BFS/Dijkstra）で自動発見する。
  • 具体例：「Feを含む安定なB2化合物」の場合
    • 必要テーブル: material_entry（中心）, composition（元素Fe）, structure（B2）, phase_stability（安定性）
    • 不要テーブル: calculation, calculated_property, data_source
    • Schema Graphが自動的に3つのJOIN経路を特定

4.2 SQL-as-Few-Shot-Examples（RAGフィードバックループ）

成功したクエリを蓄積し、類似の新規クエリ時にLLMプロンプトへ注入する自己改善ループ：

  1. ユーザーのNLクエリが成功（SQL生成→実行→結果返却）
  2. (NL, SQL, conditions, row_count) のタプルをJSONLファイルに蓄積
  3. 新しいクエリが来たとき、TF-IDFコサイン類似度で上位3件を検索
  4. 検索された事例をLLMプロンプトの few-shot examples セクションに注入
  5. LLMは過去の成功パターンを参考にしてSQLを生成
Few-Shot Store の初期状態： 手動で用意した 7件のシード事例 + 論文から抽出した 4件 = 計11件でスタート。 運用を続けるにつれ、成功事例が蓄積されて精度が向上する設計。

5.3 Naive T2SQLの具体的問題

Naive（Level 0）が生成するSQLの典型的な問題を示す。

例: A01「Feを含むB2化合物を出して」

Level 0: Naive SQL

SELECT m.entry_id, m.formula, s.prototype FROM material_entry m JOIN composition c ON c.entry_id = m.entry_id JOIN structure s ON s.entry_id = m.entry_id JOIN phase_stability ps ON ps.entry_id = m.entry_id JOIN calculation calc ON calc.entry_id = m.entry_id JOIN calculated_property cp ON cp.calculation_id = calc.calculation_id WHERE s.prototype = 'B2' AND c.element = 'Fe';

問題点:

  • Unnecessary JOINs: calculated_property, calculation, phase_stability
  • No LIMIT clause — unbounded result set
  • No DISTINCT — may return duplicate rows from JOINs
  • No SQL safety validation (sqlglot/forbidden keyword check)

Level 1: Schema Graph SQL

SELECT DISTINCT m.entry_id, m.formula, s.prototype, s.lattice_a, s.space_group FROM material_entry m JOIN composition c ON c.entry_id = m.entry_id JOIN structure s ON s.entry_id = m.entry_id WHERE (s.prototype = 'B2' OR s.strukturbericht = 'B2') AND c.element = 'Fe' LIMIT 100;

改善点: 必要な2テーブル(composition, structure)のみJOIN。DISTINCT・LIMIT付き。

11. Pros / Cons 総括

11.1 コスト・ベネフィット

Fig.7: 左: 平均レイテンシ比較（対数スケール）。右: 1クエリあたりAPIコスト（円）。

11.2 Level 0: Naive T2SQL

Pros

  • 実装が最も単純（条件抽出→全テーブルJOIN）
  • 外部依存なし（LLM API不要、NetworkX不要）
  • 処理速度が速い（~50ms）

Cons

  • 致命的：不要テーブルのJOINにより結果行が増殖（calculated_property × calculation のCROSS JOIN的効果）
  • 致命的：複数元素AND検索（「NiとAlを両方含む」）でEXISTS構文が使えず、0件になる
  • LIMIT/DISTINCTなし→大量結果返却
  • SQL安全検査なし→SQL injection脆弱
  • 実用には不適

11.3 Level 1: Schema Graph T2SQL (Rule-based)

Pros

  • API不要：完全オフライン動作。機密データを外部に送信しない
  • 高速：平均 <100ms（Naive比で同等、LLM比で70倍高速）
  • 決定的出力：同じ入力に対して常に同じSQLを返す（再現性）
  • 安全検査完備：SQL Guard, DISTINCT, LIMIT自動付与
  • コスト0：APIコストなし
  • Schema Graph：最小JOIN経路の自動探索で正確なSQL

Cons

  • 辞書依存：material_terms.yamlに未登録の用語（Xe, Rn, 「ヘスラー合金」等）は警告なしに無視される
  • 数値条件不可：「band_gap > 1.0 eV」のようなWHERE句を自動生成できない
  • 固定パターン：辞書にないクエリパターンには一切対応できない
  • Silent Failure：認識できなかった条件が無視されてもユーザーに通知しない
  • 表記揺れ非対応：スペルミス（Nickle→Nickel）やひらがな（にっける）に非対応

11.4 Level 2: Schema Graph + LLM (GPT-5)

Pros

  • 未知語対応：辞書に未登録のXe, Rn等も認識可能（B01で実証済み）
  • 意図理解：「NiAlのL12」のような略記から正確に意図を推定（C09で1件のみ返却）
  • 数値条件生成：「band_gap > 1.0 eV」のWHERE句を生成可能
  • Few-Shot効果：過去の成功事例を参考にして精度が向上する自己改善ループ
  • 多言語対応：日本語・英語の自然文を柔軟に処理
  • Schema制約：許可テーブル/カラム/JOINのみをプロンプトで指定し、ハルシネーションを抑制

Cons

  • レイテンシ：平均7.3秒/件（Rule-basedの~70倍）。インタラクティブ利用に不向きな場合あり
  • APIコスト：1クエリあたり~1,500トークン（~¥9）。大量クエリでコスト累積
  • ハルシネーション：存在しないテーブル/カラム名を生成する可能性（Schema制約で軽減するが完全ではない）
  • 非決定的：同じ入力に対して毎回異なるSQLを返す可能性（再現性の問題）
  • オフライン動作不可：API接続が必須。ネットワーク障害時は使用不能
  • セキュリティ：ユーザーのクエリ内容がOpenAI APIに送信される。機密データを含むクエリには不適切
  • GPT-5固有：temperature制御不可（デフォルト1のみ）、内部推論に大量トークン消費

12. デメリットと限界（忖度なし）

本システムの100%パス率が持つ意味と持たない意味を、深刻度順に列挙する。

深刻度#デメリット詳細材料研究者にとっての意味
高1 テストケースの自己参照性 テストケースはシステムの抽出パターンを知っている開発者が設計。「自分で作った試験を自分で受けている」状態。 100%は当然の結果であり、実力の証明ではない。 第三者の材料研究者が自由文で入力した場合のパス率は不明。実運用前に必ず第三者評価が必要。
高2 Few-Shot RAGの効果が未実証（Rule-basedモード） Rule-basedモードではFew-Shot事例は「蓄積するだけ」で、SQL生成には使われない。 Few-Shotの本来の効果（LLMプロンプトへの事例注入による精度向上）はLLMモードでのみ有効だが、 LLMモードでも明確な精度差として定量化できていない。 「RAGで改善する」と説明しているが、実際のRule-basedパイプラインではRAGの恩恵は0。 LLMモードでの効果も、Few-Shotあり/なしの比較実験が未実施。
高3 OQMD比較は循環論証 OQMDから取得したデータをDBに投入し、同じ条件でクエリして「100%一致」と報告。 同じデータの同じクエリなので不一致が起きる方がおかしい。 「OQMDと100%一致」は「データ投入パイプラインが壊れていない」ことの検証であり、 T2SQLの精度評価ではない。
中4 Silent Failure（無言の失敗） 辞書未登録の用語（Xe, 「ヘスラー合金」等）が検出されずにクエリから除外されても、 ユーザーへの警告がない。ユーザーは条件が無視されたことに気づかない。 例：「Xeを含むB2化合物」→ Xeが無視されて全B2が返される。 研究者は「Xeを含むB2は636件もある」と誤解する。
中5 数値比較条件の生成不可（Rule-based） 「band_gap > 1.0 eV の化合物」のようなWHERE句を自動生成できない。 post-filtering（全件取得後にPythonで絞り込み）で代替。 材料研究で頻出する閾値指定（「形成エネルギーが -0.3 eV/atom 以下」等）に対応できない。 LLMモードでは対応可能だが、APIコストとレイテンシが発生する。
中6 曖昧クエリのフォールバックが危険 「今日の天気を教えて」→ 全データ LIMIT 100 を返す。 材料と無関係なクエリに対して材料データが返ることで、ユーザーが誤解する可能性。 「この質問には回答できません」と明示的に拒否する方が安全。 現在の設計は「何かしら返す」ことを優先しているが、False Positiveのリスクが高い。
低〜中7 スキーマが単純すぎる 7テーブルの簡易スキーマ。実運用の材料DB（AFLOW: 数十テーブル、NOMAD: 数百カラム）と比べて 大幅に単純。Schema Graph Traversal の真価は複雑スキーマでこそ発揮されるが未検証。 本検証結果は「7テーブルでの概念実証」であり、「実運用DBでも動く」という保証ではない。
低8 データ規模が小さい 909件 ≈ OQMD全体(100万件超)の0.1%未満。 大規模データでのインデックス設計、クエリ性能、LIMIT 100の妥当性は未評価。 900件なら全件スキャンでも瞬時だが、100万件では適切なインデックスなしでは秒単位のレイテンシ。
低9 表記揺れ非対応 「ニッケル」→Ni は対応済み。「にっける」（ひらがな）、「Nickle」（スペルミス）は未対応。 実際の研究者は表記が不統一。特にメール・チャット経由でのクエリでは略記・ミスが頻発する。
低10 エラーリカバリ不在 SQL実行エラー時に「別のSQLを試す」「ユーザーに確認する」リカバリ機構がない。 LLMモードにはrepair_loop（再生成）があるが、Rule-basedモードは1回失敗でそのまま終了。 Rule-basedモードではSQL構文エラーが起きたら即座に失敗。研究者は原因が分からない。
