2. 実験設計

2.1 背景と動機

7テーブル星型スキーマでの先行実験では、LLM+Schema条件が100%を達成し天井効果が生じた。 スキーマが単純すぎるとLLMが全JOINパスを「暗記」可能であり、Traversalの必要性が見えなくなる。 本検証では、OQMD実規模（~30テーブル）に近い複雑スキーマでTraversal効果を定量測定する。

4. Schema Graph Traversalの仕組み

4.1 問題：30テーブルの全スキーマを注入すると何が起きるか

Full Schema注入の問題点：
  • LLMのコンテキストウィンドウを圧迫（30テーブル×平均6カラム = ~180行のYAML）
  • 類似名カラムの曖昧化（例：entry_idが複数テーブルに存在→ ambiguous reference）
  • 不要テーブルとのJOINを生成（スキーマに見えるので「念のためJOIN」する）
  • FK経路の誤選択（直結でないテーブルを直接JOINしようとする）

4.2 Traversalの3段階

  1. テーブル特定：クエリから参照テーブルを辞書＋LLMで特定
  2. FK走査（Steiner木近似）：特定テーブル間の最小FK経路を計算
  3. サブセット注入：走査結果の関連テーブルのみをプロンプトに注入

これにより、LLMは「必要なテーブルだけ」を見てSQLを生成する。 カラム名の曖昧化が解消され、不要JOINの生成が防止される。
